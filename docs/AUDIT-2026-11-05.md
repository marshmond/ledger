# Ledger audit: where the app stands and what to build next

Date: 2026-11-05. Read-only audit at commit `32a20d6`. No application files were changed. Contains no personal or financial data.

## How much was checked

- **Run:** `npm test` (1,050 tests in 72 files pass); `tsc --noEmit` (clean); `npm audit --omit=dev` (0 vulnerabilities). Production bundle 1.27 MB (369 KB compressed).
- **Read in full:** `package.json`, deploy workflow, `vite.config.ts`; `src/db.ts`; all of `src/core/`; all of `src/lib/sync/`; `lib/backup.ts`, `lib/backupFile.ts`, `lib/autoBackup.ts`; Tasks and Calendar models and data layers; Ledger's registration, records and due provider; README; the top ~260 of 1,181 lines of `docs/BACKLOG.md`; the hooks, sync, roadmap and Phase 3 audit docs.
- **Measured with search:** module-to-module imports, pages that touch the database directly, `localStorage` use, which shared tables are actually used.
- **Not done:** the app was not opened in a browser (the deployed address returned HTTP 200, nothing more); GitHub Actions status not checked (`gh` not installed); sync not tested against real GitHub or two real devices (the backlog says this has never been done); phone speed not measured; very little of the 66 page files, the ~127 files in `src/lib` (payroll, Roth, projection, loans) or the tax tables was read; money and tax logic was NOT audited for correctness.

## 1. Executive summary

**Overall.** Unusually disciplined for a one-person project: 1,050 tests, versioned migrations, encrypted backups and sync, and a written contract for how modules plug in. It is a mature finance app with a small, well-designed module layer around it. It is not yet a platform.

**Architectural maturity.** The module layer is solid. The shared data foundation is half-built, and the sync design will limit what can be added next.

**Biggest strengths.**
1. The module registry (`src/core/registry.ts`): modules contribute due dates, search, Add-box destinations, Today cards and linkable records; clashes are caught at start-up.
2. Derived, not copied: bills, vests and tasks appear on the Calendar as computed views (`core/dueProvider.ts`), so no stale or doubled copies after sync.
3. The preview-then-commit pattern: the Add box's `QuickAddDef` (`parse` → "Will add: …" preview → `commit`, optionally with undo) is already the shape a safe AI action layer needs.
4. Sync and backup coverage: sync walks every table automatically; encrypted, tested, soft deletes, a "lost edit" safety list.
5. Defensive reading of stored records (`asTask`, `asEvent`) tolerates records from other devices or versions.

**Biggest limitations.**
1. Sync sends the entire database as one file each time (section 4).
2. Ledger has no "write" layer. 51 of 66 page files import the database and about 118 write calls sit in `src/pages`. Tasks and Calendar do have command functions (`createTask`, `completeTask`, `retireEvent`). An assistant or a Project cannot safely create a transaction without copying screen logic.
3. Links and attachments are thin. `links` is used only for "task or event is about X". `attachments` and `dueItems` are used by no screen. Nothing checks that a link target still exists.
4. Calendar is secretly the shared kernel: Tasks imports its recurrence engine, time helpers and pickers; Today imports its data hook.
5. The GitHub token and passphrases sit in plain `localStorage`.

**Most important opportunities.** About one phase of foundation hardening, then Projects. Put the assistant's rules in the registry the way Add and Search work. Use Tasks' existing "repeat after completion" mode as the home-maintenance engine.

## 2. Current-state architecture

### Stack (verified from `package.json`)
- React 19.3, react-router-dom 7 (`HashRouter`), Dexie 4 over IndexedDB with `dexie-react-hooks`, PapaParse for CSV.
- TypeScript 7, Vite 8, Vitest 5, `fake-indexeddb` for tests.
- No charting library: charts are hand-drawn SVG (`src/ui/charts.tsx`, `src/pages/charts.tsx`). No UI component library, no state library, no test library for screens.
- About 45,000 lines of TypeScript: `src/lib` ~19k, `src/pages` ~11.5k, the rest ~14k.
- Deploy: `.github/workflows/deploy.yml` runs `npm ci`, `npm test`, `npm run build`, then publishes `dist/` to GitHub Pages on every push to `main`. A failing test blocks the deploy.
- Offline: `public/sw.js` service worker (pages network-first, assets cache-first).

### Structure and flow

```
Browser (static site on GitHub Pages)
 main.tsx - installTracking(db), seed, startAutoSync, startAutoBackup -> App.tsx
   ModuleBar - GlobalFrame (Search, Add box) - TaskCreator - Routes /<module>/*
       |
       +- Modules (modules/index.ts): Today, Ledger, Calendar, Tasks
       |    each = ModuleDef { Component, routePaths, nav, contributes{...} }
       |    contributes: dueProvider, records, createFromEvent,
       |                 todayCards, searchSource, quickAdd
       +- core/: registry, store (repo, links), dueProvider, bridges (task/event)
       v
 Dexie DB "ledger" v15 (IndexedDB), 40 tables
   34 Ledger tables (typed, one per concept)
    6 shared: contacts, tags, links, moduleRecords (Tasks + Calendar live here as JSON),
              attachments*, dueItems*        (* defined, unused by any screen)
       |
       +- lib/backup*   manual export/restore: plain JSON or AES-GCM encrypted
       +- lib/sync/*    ALL tables -> JSON -> gzip -> AES-GCM -> one file in a private GitHub repo
```

### Navigation and state
- Addresses look like `#/ledger/budget`. `core/router.tsx` wrappers add each module's prefix so pages still say `/budget`; `core/legacy.ts` forwards old pre-module addresses; a setting chooses the landing module (Today by default).
- No global store. Data screens subscribe with Dexie's `useLiveQuery` (381 uses). `core/sharedLive.ts` shares one live query among several Today cards. Per-device preferences go in `localStorage`; shared settings in the `settings` table.

### Data and persistence
- All data lives in the browser's IndexedDB; no server.
- `newId()` (`lib/sync/track.ts`) makes time-based ids. Built-in records use fixed ids around 9e15 so two devices create the same record.
- `installTracking` stamps `updatedAt` on every write to every table; this is the basis for sync.
- 15 versioned Dexie migrations; version 15 only added tables.
- Backup: `exportAll` / `importAll` (`lib/backup.ts`) list all 40 tables by hand. `backupFile.ts` checks a file before restoring; `CURRENT_SCHEMA_VERSION` is tested against the Dexie version.
- Sync: `lib/sync/merge.ts` is a pure, tested merge. Later edit wins per record; the losing version is saved for recovery; deletions tracked for a year.
- Security (verified): PBKDF2 (310,000 iterations) then AES-GCM; the price-API key is never exported or synced; no HTML-injection sinks in `src`.

## 3. Module-by-module

| | Finance (Ledger) | Calendar | Tasks |
|---|---|---|---|
| **Does** | Accounts, budget, forecast, income and tax, investments, debt, retirement, Roth, reports (README lists all) | Month, week, agenda; repeats with exceptions; reminders; `.ics` export; event types (Bill, Finance date, Birthday) | Quick-add shorthand, views, lists, tags, checklists, repeats (`fixed` or `after` completion), bulk actions |
| **Data** | 34 typed tables (`src/types.ts`) | `moduleRecords` kinds `event`, `calendar` (`calendar/model.ts`) | `moduleRecords` kinds `task`, `list` (`tasks/model.ts`) |
| **Write path** | Directly from screens | `calendar/data.ts` | `tasks/data.ts` |
| **Offers others** | Due dates, linkable records, Bill-to-scheduled handoff, Today cards, search, Add | Search, Add (event) | Due dates, search, Add (task), "Add task" on Ledger records |

**Shared foundation?** Partly. They share the database, the registry, the contact/tag/link tables and the Today, Search and Add surfaces. Underneath there are two storage styles (Ledger typed tables; Tasks and Calendar JSON records) and different write layers.

Findings that bear on what comes next:
- Only Ledger registers `records`. Tasks and Calendar don't, so nothing can link *to* a task or event through the pickers yet.
- Two kinds of "person": Ledger's `people` (name, birth year, used for tax math; 17 uses) versus the shared `contacts` (name, relationship, notes). Birthdays link to `contacts`. A Family module has to reconcile them.
- `properties` is a value tracker (name, kind, linked loans, value history): no maintenance, warranty or document fields.
- Tasks have `contactIds` but no assignee.

## 4. Architecture and technical debt

**Working well, leave alone:** the registry and hook contracts; derived Calendar items; soft deletes in the shared store; the merge function and its tests; the separate sync-meta database; Ledger's calculation engines in `src/lib` (well tested; rewriting is risk with no payoff).

**Real risks, ranked**
1. **Whole-database sync.** `snapshotOf` reads every table. Each sync downloads, decrypts and merges the whole file, then re-encrypts and uploads it (PBKDF2 runs in both directions). Runs happen on open, on return to the tab, 8 seconds after a change and every 5 minutes. Every upload is a new git commit holding a new blob that cannot compress against the last, so repository history grows with every change. UNVERIFIED: the real encrypted file size and repository size. Documents with file contents cannot go through this path.
2. **Record-level conflicts on JSON records.** An event keeps its single-date overrides inside one record. A project holding its milestones in a list would lose edits made on two devices. Design new modules as many small records.
3. **No referential integrity.** `links` stores free-text ids like `account:12`. Deleting the target leaves a dangling link, noticed only when something tries to show it. `dueItems` is dead code still carried in every backup.
4. **Backup completeness depends on memory.** A new table must be added in `db.ts`, `exportAll`, `importAll`, the `BackupFile` type and `backupFile.ts`. No test was found asserting that every Dexie table is in the backup.
5. **Credentials in plain `localStorage`** (`lib/sync/auto.ts`, `lib/autoBackup.ts`): sync token, sync passphrase, auto-backup passphrase. Browser storage is scoped to the origin (`marshmond.github.io`), not the `/ledger/` path, so any other GitHub Pages project under the same account could read this app's database and token. Standard browser behaviour; not tested here. No Content-Security-Policy check was made.
6. **Calendar acts as the shared kernel.** Tasks imports `calendar/recurrence`, `model`, `time`, `pickers`, `parts`, `RepeatFields`; `tasks.css` leans on `calendar.css`; Calendar's `quickEvent` reuses Tasks' parser; Today imports Calendar's `useCalendarData`. Cheap to fix now, expensive later.
7. **No automated screen tests.** Tests run in plain Node with no browser simulation; UI was checked by hand.
8. **Two-device sync has not been tested on real devices** (per the backlog), yet it is relied on.
9. **Smaller:** 38 browser `confirm()` pop-ups remain; one 369 KB (compressed) bundle with no lazy loading; dates computed through UTC at 8 call sites, two of which look wrong for evening timezones (`calendar/model.ts:86`, `calendar/searchSource.ts:15`; not reproduced in a browser).

**Theoretical, not real:** dependencies (six runtime packages, no vulnerabilities, pinned by lockfile); the single-file service worker.

**Fix before expanding:** backup coverage test; move recurrence, time and pickers into `core/` or `ui/`; register `records` for Tasks and Calendar; extract only the Ledger write functions Projects and the assistant need (create, edit, categorize a transaction); replace UTC date calls with local-date helpers; show real sync file and repo size on the Sync page; decide how the token is handled.

## 5. Future-state architecture

```
Shell (module bar, Today, Search, Add box, Assistant panel)
 ------------------------------------------------------------
 Modules:  Ledger | Calendar | Tasks | Projects | Home & Assets | Documents*
 ------------------------------------------------------------
 Shared kernel (core/): recurrence & time | registry | links | tags | contacts
                        | activity log | action registry | file store*
 ------------------------------------------------------------
 Storage: Dexie tables (Ledger) + moduleRecords (small JSON modules)
 Sync: records, later files by hash        Backup: auto-complete + tested
                                                     (* later)
```

**How modules interact.** Keep the three rules the code already follows: the owner module is the only writer of its records; others reach it through the registry, not imports; anything with a date is derived, not copied.

**Shared pieces to add.** A `projectId` on records that belong to a project; an activity log (who or what changed what, with an undo handle), essential once an assistant writes data; Contacts v2 (phone, email, address, birthday, role) for vendors and warranty providers.

**Household configuration today.** Per-person and per-year settings live in the `settings` table and `localStorage`. Tax logic is in code and assumes married filing jointly and Massachusetts (`src/data/taxYears.ts`, `retirementTax.ts`). Keep it as is; if another household ever matters, wrap tax tables as a swappable "rules pack" rather than touching the finance code now.

**The assistant, built on existing patterns.**
- Add `contributes.assistantTools` beside `quickAdd`: each tool declares inputs, read or propose type, and a preview.
- Read tools return the smallest useful answer and respect "Hide amounts"-style scopes.
- Write tools only propose; the user confirms in the same "Will add: …" card. Money-moving and deleting tools stay out at first.
- The activity log records everything the assistant did, with undo.
- Privacy catch: this is a static site, so a language model means sending household data from the browser to an outside service, which breaks today's "nothing leaves your device" promise. It needs an explicit decision (section 8).

## 6. Roadmap recommendations

| # | Initiative | Effort | Depends on |
|---|---|---|---|
| 0 | **Foundation hardening:** backup test, extract shared kernel, register Tasks and Calendar `records`, minimal Ledger write functions, local-date fix, sync size display | Medium | none |
| 1 | **Projects MVP** (section 7) including Contacts v2 for vendors | Medium | 0 |
| 2 | **Home & Assets** (merges roadmap items 3 and 5): extend `properties` with maintenance items as repeating tasks ("repeat after completion"), warranty dates, vendor contacts; documents as records with a link, not files | Medium | 0, 1 |
| 3 | **Read-only assistant** plus the activity log; then propose-and-confirm for tasks, events, projects | High | 0 and the privacy decision |
| 4 | **Documents with real files:** file store, search, file backup | High | rethink of sync |

**Why this order.** Projects first is right. The assistant doesn't need Projects but does need the hardening work; building it earlier means building it twice. "Recurring responsibilities" mostly exists (repeating tasks); what is missing is a template and a home for it, which is Home & Assets. Contacts is not last: Projects and Assets need vendors.

**Missing from the roadmap:** reminders and notifications (deferred in the backlog; routines are weak without them); the activity log; an assignee or owner on tasks; a real two-device sync test; an orphan-link check screen.

**Explicitly not yet:** email integration (no server, so OAuth would run in the browser; Google's requirements for mail access from a static page are UNVERIFIED; start with paste or forward into Documents); file storage inside the current sync; a cross-module "everything" query layer; multi-household or commercial features.

**Key tradeoff.** A small server would solve sync, notifications and the assistant together but ends "no server, no account". Not assumed.

## 7. Recommended Projects architecture

**Entities** (stored as `moduleRecords`, module `projects`; no migration, covered by backup and sync):

| Kind | Key fields |
|---|---|
| `project` | name, status, start and target dates, budget target (cents), notes, vendor contact ids |
| `budgetLine` | projectId, name, planned cents, optional categoryId |
| `commitment` | projectId, vendor contact, amount, status (quoted, agreed, invoiced, paid), optional budgetLineId |

One record per line and per commitment, never a list inside the project, so two devices editing different lines don't overwrite each other.

**Connections**
- **Tasks, events, transactions:** optional `projectId` field. An item belongs to at most one project, so this is a parent pointer, not a many-to-many link. Optional fields need no migration; scanning 20,000 transactions took about 8 ms in the owner's earlier measurements.
- **Milestones:** a task with an `isMilestone` flag and a due date, so they reach Calendar, Today and Search through the existing Tasks due provider.
- **Money:** Actual = transactions with that `projectId`, computed by Ledger through a registered read function (Projects never writes transactions). Committed = commitments. Planned = budget lines. Budget lines may reference a Ledger category if the project should appear in the envelope budget (optional).
- **Documents (later):** `links` of type `attached`; until files exist, a record with a name, date and pointer.

**Reuse:** Tasks' editor and list components, Calendar's date and recurrence pieces (after extraction), the Add box (add "Project" as a destination), Search, a Today "Projects" card through `todayCards`, and Ledger's Transactions filter (add a project filter).

**Minimum viable version**
1. Create a project with name, dates, total budget.
2. Add budget lines and commitments.
3. A project page showing planned vs committed vs actual, its tasks, milestones and events.
4. A project box on the transaction form, and "Add task" from the project.
5. A Today card for upcoming milestones.

Skip Gantt charts, templates, file upload and invoicing.

## 8. Decisions for the owner

1. **Should the assistant send household data to an outside AI service?** It ends "nothing leaves your device". Default: yes, only the smallest slice per question, with your own key stored on the device, money fields off unless switched on, and a visible log of what was sent.
2. **Small server at some point, or stay serverless?** Default: serverless for now; reconsider for push notifications or documents.
3. **One person's data, or several household members?** Changes sync, assignees and permissions. Default: one shared household login.
4. **How should the GitHub token and passphrases be stored?** Default: keep, add an optional lock that encrypts them with a device passphrase, and keep this app on its own GitHub account or custom domain.
5. **Project-to-transaction link: field or tag?** Default: a `projectId` field.
6. **Contacts v2 inside Projects or its own step?** Default: inside Projects, minimal.
7. **Documents: metadata and links first, real files later?** Default: yes.
8. **Reminders: real notifications in the foundation phase, or wait?** Default: wait (calendar alerts through `.ics` are the cheap route).
9. **Extract the shared kernel out of Calendar now?** Touches many files, changes no behaviour. Default: yes, first step of Phase 0.
