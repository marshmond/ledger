## A. Synchronisation

### What happens in one sync run (from `engine.ts`)
1. Read every table into memory (`snapshotOf`).
2. List the repository's files, download the whole sync file, decrypt it (key derivation, about 310,000 rounds, once), decompress, parse.
3. Merge record by record (`mergeSnapshots`).
4. Write the merged result locally in one IndexedDB transaction.
5. Only if the merged result differs from the remote copy: compress, encrypt (key derivation again), upload with the old file's version id.
6. Only after that: save the list of known record ids and the sync time.

A run happens on open, on return to the tab, when the connection comes back, 8 seconds after any change, and every 5 minutes while the app is visible.

### Measured (Node 22, invented data)
Data: the stated number of transactions, plus 12 accounts, 60 categories and one task-sized record per 10 transactions. Payee names come from a list of 15, so this data is probably **easier to compress than real data**; treat sizes as the low end.

| Transactions | JSON | Encrypted sync file | Encode + key derivation | Decode + key derivation | Merge |
|---|---|---|---|---|---|
| 2,000 | 0.59 MB | 103 KB | 75 ms | 44 ms | 32 ms |
| 10,000 | 2.9 MB | 509 KB | 90 ms | 65 ms | 160 ms |
| 30,000 | 8.7 MB | 1.5 MB | 290 ms | 136 ms | 562 ms |
| 100,000 | 29 MB | 5.1 MB | 674 ms | 638 ms | 3.4 s |

Key derivation alone is about 54 ms on this PC.

### Findings
- **Size is a straight line:** about 50 KB encrypted per 1,000 transactions here. Allow up to 1.5x that for real data.
- **Encryption is not the bottleneck.** The merge (it compares every record by turning it into text) is the biggest cost, and it runs over *all* records on every run, even when nothing changed. Phones are slower than this PC (by how much is UNVERIFIED); at 10,000 transactions the merge is still a fraction of a second here.
- **Every run downloads the whole file**, even when nothing changed, because `getFile` always fetches the file's content after listing it. The listing already returns the file's version id; if it equals the one this device last saw and nothing changed locally, the download could be skipped. Cheap fix (B4 below).
- **Repository growth is the real limit.** Every upload is a new commit holding a new encrypted blob that cannot be compressed against the last. Growth per year is roughly (uploads per day) x (file size) x 365. An upload happens only when the merged result differs from the remote copy, so roughly once per burst of editing on either device. Assuming 10 uploads a day:

| File size (about) | Per year |
|---|---|
| 100 KB (2,000 txns) | 0.37 GB |
| 500 KB (10,000 txns) | 1.8 GB |
| 1.5 MB (30,000 txns) | 5.5 GB |

  GitHub's published guidance (recalled, not re-checked) is to keep repositories under about 1 GB and strongly under 5 GB. A 10,000-transaction household at 10 uploads a day passes 1 GB inside a year. The actual number of uploads per day is not known; the Sync page should count them (B4).
- The weekly encrypted backup is JSON text encrypted **without compression** (then base64), so each copy is about 4x larger than the sync file. Eight copies are kept, but deleted copies stay in git history. About 200 MB a year at 3 MB of JSON. Low priority (C).

### Two devices change different records
Merged record by record; both changes survive. Covered by tests (`sync.test.ts`: "different records edited on each device while apart", "start from one device… changes flow both ways", the tasks and calendar variants). Verified by test only; not on real devices.

### Two devices change the same record
- The later `updatedAt` wins **for the whole record**. The losing version is saved in full (up to 50 notices) and can be put back (`restoreLostVersion`). Tested.
- Consequence for design: two devices editing *different fields* of one record still lose one edit (recoverably). Tasks and events keep all their fields in one JSON record. **Projects must keep one record per fact** (a budget line, a commitment), never a list inside the project.
- "Later" is each device's own clock. A phone clock a few minutes fast can make an older edit beat a newer one. No test covers clock differences (UNVERIFIED; risk is small for one household).

### Sync fails or is interrupted
| Where it stops | Result |
|---|---|
| Before the local write | Nothing changed. |
| During the local write | One IndexedDB transaction: all or nothing. |
| After the local write, before upload succeeds (network lost) | This device has the other device's changes; the remote lacks this device's. The saved sync state is not updated. Next run merges again and gets the same answer. Safe. |
| Another device uploaded first (HTTP 409/422) | Treated as a conflict: re-read, merge again, up to 3 attempts. Tested ("retries when another device syncs at the same moment"). |
| Upload succeeded, tab closed before the sync state was saved | Next run starts from older state. That state is only used to spot deletions and report conflicts, and its errors lean towards keeping data. Safe. |
| Wrong passphrase or damaged file | Fails with a clear message before anything is written. |

Gaps: no test simulates a failure *between* upload and state save, or a network drop in the middle of the upload (UNVERIFIED by test; reasoning above is from reading the code). No retry delay, no history of past errors. A device offline for over a year could bring back deleted records (deletion markers are kept 365 days; by design).

### Recommendation
**Monitor now; two small fixes soon; redesign only at triggers.** Sync is not a Projects blocker (Projects adds a few hundred small records).
- Soon: show file size, record counts, uploads per day and last upload on the Sync page; skip the download when the file's version id is unchanged and nothing changed locally (B4).
- Redesign triggers (any one): encrypted file over about 5 MB; repository over about 800 MB; a sync run over about 3 seconds on the phone; documents or attachments are wanted.
- When triggered, in order of cost: (1) lower upload frequency; (2) periodically replace the repository's history with a single fresh commit (needs a feasibility check with a fine-grained token; UNVERIFIED); (3) split the file by table or by year of transactions with a small index file; (4) a small backend.
- **Manual test the owner can run** (use a separate test repository, a test token and a second browser profile, never real data): (1) set up sync on profile A with the test repo, add a few invented accounts and 10 transactions; (2) on profile B choose "replace from synced copy"; (3) set B offline in browser tools, edit transaction X on B and a different transaction Y on A, bring B online, confirm both edits reach both; (4) edit the same transaction on both, confirm the later wins and the other appears as an overwritten edit you can put back; (5) start a sync, switch to offline mid-way, reopen, confirm nothing is lost; (6) import a synthetic CSV with about 5,000 rows, note the file size on GitHub and the commit count after a day of normal use; (7) set one profile's clock 5 minutes ahead and repeat step 4.

## B. Backup and restore completeness

### Evidence
A script compared the 40 table declarations in `db.ts` with each list in the backup code. All 40 are present in all five places:
`db.ts` fields, `exportAll`, `importAll` (the table list used to clear), `importAll` (the inserts), the `BackupFile` type. They are also in `OPTIONAL_LISTS`/`REQUIRED` in `backupFile.ts`.

**Cost of one new table today:** the above plus `importAll`'s accepted-version list, the `version` type union and `CURRENT_SCHEMA_VERSION`, about 8 hand edits, plus a Dexie migration. Nothing fails loudly if one is missed. Existing tests check that the schema version matches (`backupFile.test.ts:17`) and that a sample file round-trips (`:68`), but **no test enumerates the tables.**

### Other findings
- **Sync is automatic:** it walks `d.tables`, so a new table is synced without anyone remembering. Backup is the only hand-kept path.
- **Future `moduleRecords` entities are covered automatically** (one table, all kinds). Probed: an extra field on a transaction survives backup, restore and the sync snapshot (so `Txn.project` needs no backup change either).
- **Restore safety is good:** checks the file first (`checkBackupText`), refuses newer versions with a clear message, upgrades older ones by filling missing lists, runs in one transaction (test: "a failed restore leaves existing data untouched"), offers a pre-restore copy.
- `MIGRATIONS` in `backupFile.ts` is empty. Every version so far only added tables. The first change that alters existing data will need a step there and a test with an old-version sample.
- Restoring rewrites every record's `updatedAt` to now (the change-tracking hook fires on insert). This makes the restore win at the next sync, which is intended.

### Recommendation
1. **Test first (A1):** for every name in `new FinanceDB().tables`, assert it appears in the export, in the file checker's lists, and survives export to restore into an empty database with one synthetic row per table (compare ignoring `createdAt`/`updatedAt`). Also restore a synthetic version-1 and version-14 file.
2. **Then, optionally, remove the cause:** build the lists from `d.tables` so a table cannot be left out. Keep the test as the guard. Mind the fixed-id insert-order rule from `CLAUDE.md`; restore uses explicit ids so ordering should not matter, but the test above will show it.
3. Compress the encrypted auto-backup (C).

## C. Credentials and browser security

### What is stored
| Item | Where | Sensitivity |
|---|---|---|
| GitHub fine-grained token | `localStorage` `ledger-sync-config` | High. Read and write on one repository. What it can reach is encrypted (see below). |
| Sync passphrase | same entry | Critical. Decrypts the sync file and everything in the repository. |
| Auto-backup passphrase | `localStorage` `ledger-autobackup` | Critical for the backup copies. |
| Price-lookup API key | IndexedDB `settings`, never backed up or synced | Low (free-tier quota) |
| **The financial data itself** | IndexedDB, **not encrypted** | The real asset |

The sync screen already tells the owner to create a *fine-grained* token limited to *one repository*. That is the right setup; whether the owner's actual token follows it is UNVERIFIED.

### Who can read it
Browser storage belongs to the **origin** (scheme + host + port), not the folder. Any script on the same origin reads all of `localStorage` and IndexedDB, including the unencrypted data. So moving or encrypting the localStorage entries would not stop such a script; it could just read the database.

### Realistic threats, for one household on its own devices
1. **GitHub account takeover.** The repository deploys the code that holds all the data. Anyone who controls the account can ship a modified app to every device. This is the biggest real risk.
2. **Other content on the same web address.** GitHub Pages project sites under one account share one origin. If another Pages site exists (now or later), its scripts could read Ledger's data. UNVERIFIED whether one exists.
3. **Lost or unlocked device.** Covered by the device's own lock screen; the app can add little.
4. **A bad dependency or GitHub Action.** Six runtime packages, locked and audited clean (per the audit). Actions are referenced by version tag (`@v4`), not pinned to a commit. Low probability.
5. **A script injected into Ledger itself.** Low: the audit found no HTML-injection points and no third-party scripts.
6. **Token theft.** Limited: the attacker gets only encrypted files. They could overwrite or delete the sync file or backups (a nuisance: sync would stop with a "wrong passphrase or damaged" message, and local data and the first-sync safety copy remain).

### Content security
None. Neither `index.html` nor the deploy sets a Content-Security-Policy, and GitHub Pages cannot send headers, so a `<meta>` tag is the only route (it cannot do `frame-ancestors`). `index.html` has two small inline scripts for the theme, which a policy must allow by hash or by moving them to a file. Data leaves the browser only to `api.github.com` and `api.twelvedata.com` (the only `fetch` calls found), so an allow-list is short: `connect-src 'self' https://api.github.com https://api.twelvedata.com`, `object-src 'none'`, `base-uri 'none'`, `form-action 'none'`. Value: if a script ever got in, it could not send data to an arbitrary server. It does not stop it *reading* storage. It must be applied to the production build only (Vite's dev server needs inline scripts) and tried in a real browser, including the service worker and sync. The AI feature will add one more allowed host.

### Answers to the specific questions
- **Would a custom domain materially improve isolation?** Only if something else shares the current address. If nothing does, it adds nothing today. If something might, a custom domain (about $10 to $15 a year plus DNS set-up) or a separate GitHub account that hosts only Ledger gives the app its own origin.
- **Does encrypting stored credentials with a device passphrase help?** No, not meaningfully, for the reason you gave: the key would sit in the same browser, and the database is readable anyway. A typed "unlock" kept only in memory would protect the secrets against someone copying files off a disk, but not the unencrypted database. Not worth the friction on a phone.
- **Would a small backend help?** Not with today's threats. It would need its own way to recognise the browser, which would be another secret stored in the same place. It does help with one future thing: keeping an AI provider's key out of the browser, with spend limits and central logging. That decision belongs to the AI phase.
- **Weak spot to note:** the sync file sits in GitHub and can be attacked offline if the repository is ever exposed. The sync passphrase minimum is 8 characters. A long phrase is much stronger. The key-derivation setting (310,000 rounds) is below the figure OWASP lists for this method (600,000, recalled, not re-checked); raising it needs a new file format marker, so leave it unless the format changes anyway.

### Ranked changes
| # | Change | Benefit | Complexity | Urgency |
|---|---|---|---|---|
| 1 | Owner: turn on two-step sign-in or a passkey on the GitHub account; confirm the token is single-repository, Contents only, with an expiry | High | Low (15 minutes, no code) | Now |
| 2 | Owner: check that no other GitHub Pages site shares the address; if one does or may, move Ledger to a custom domain or its own account | High if shared, none if not | Low to medium | Now (the check) |
| 3 | Add a Content-Security-Policy `<meta>` to the production build | Medium | Low to medium (needs real-browser test) | Before any AI provider |
| 4 | Show a "use a long phrase" hint on the passphrase boxes | Low to medium | Low | Soon |
| 5 | Pin GitHub Actions to commit ids; enable Dependabot | Low | Low | Later |
| 6 | Encrypt secrets with a device passphrase | Very low | Medium | Do not do |
| 7 | Encrypt the whole local database | Real, but large | High | Do not do now |
| 8 | Small backend | None for today's threats | High | Decide at the AI phase |

### What belongs in shared code
- **Pure and light, move:** `calendar/time.ts` (used by four modules), `calendar/recurrence.ts`, the priority constants in `calendar/model.ts`.
- **Shared screens, move:** `pickers.tsx` (contact, tag and record pickers are cross-module by nature; Projects needs the contact picker for vendors and the record picker), `parts.tsx`, `RepeatFields.tsx`.
- **Leave:** Calendar's data layer, occurrences, `.ics`, and Today reading `useCalendarData` (Today is meant to read the Calendar's merged view).
- **Safest way:** move the files and leave a one-line re-export at each old path, so no other import changes and tests move with the files. Remove the re-exports later.
- **Not a strict blocker.** Projects could import from Calendar as Tasks does, but that makes a third module lean on the Calendar. Do this first inside the Projects work (B2).

### Linkable records
- Only Ledger registers `contributes.records` (accounts, scheduled items, loans, transactions by id). The record picker lists only modules that register it. Tasks and Calendar do not, so nothing can link *to* a task or event. They can register in about 40 lines each: `search`, `describe`, `openSource`. Numeric ids already work (`RecordId` is a number or text, and task links already store numeric ids). Not needed for Projects if tasks and events point to their project directly (below).

### How links are stored and resolved
- One `links` row per connection: from-module, from-id, to-module, to-id, type; soft-deleted; indexed in both directions. Created by `store.shared.links.add` (skips an exact duplicate on this device only; two devices creating the same link at once make two rows, harmless).
- Resolved at display time by asking the owning module (`recordSource(module).describe(id)`).
- **Dangling links:** a missing target shows "(no longer exists)" (`pickers.tsx` `RefLabel`). Nothing deletes or reports orphans; Ledger deletes records outright and tasks are soft-deleted, so links to both can stay. Fine for "this task is about that account". Not enough for money relationships.

### Do the proposed Projects relationships fit?
Yes, with these rules:
- Project, budget line and commitment: `moduleRecords` under module `projects`, **one record each**, children point to their parent by id inside the record (a parent pointer), not through the `links` table.
- Task and event to project: an optional `projectId` inside the task or event data. Milestone: a task with `isMilestone`, so Tasks' existing due provider puts it on the Calendar, Today and Search.
- Transaction to project: a small optional field on the transaction (section E and Deliverable 2). No database version change.
- Vendors: contact ids. Contacts currently have name, relationship and notes only; the vendor use needs phone and email (minimal Contacts v2 inside Projects).
- Reserve `links` for loose associations ("this task is about that account").

### Blocker found: unknown fields are erased
Task and event records are read through `asTask` / `asEvent`, which copy only the fields they know. Editors save from that cleaned copy. `repo.put` replaces the record's whole `data`. **Probe result (test database):** a task with extra `projectId` and `isMilestone` fields lost both after an ordinary edit, and `projectId` after "complete". Events use the same pattern (`retireEvent` saves `asEvent(r).data`; not separately probed). The note in `store.ts` ("unknown fields are kept") is true for top-level fields only.

Consequences: (a) adding `projectId` to tasks works only if every writer knows it; (b) a device running an older copy of the app would strip fields written by a newer one when it edits the record, and the loss would sync everywhere. **Must fix before Projects** (A2): keep fields the reader does not recognise when saving.

## F. Dates and time zones

# Deliverable 2: Projects financial model proposal

## Three words, one meaning each
| Word | Meaning | Where it comes from |
|---|---|---|
| **Planned** | What you intend to spend | Budget lines |
| **Agreed** (committed) | What you have accepted and owe, paid or not | Accepted commitments |
| **Paid** (actual) | Money that really moved | Ledger transactions tagged to the project |

Quotes are shown but **never counted**. Projects never creates a transaction and never stores an amount that a transaction already holds, so nothing can be counted twice.

## Entities
Stored as `moduleRecords`, module `projects`; no new tables, no migration, covered by backup and sync once A1 exists.

| Kind | Fields |
|---|---|
| `project` | name, status (planning, active, on hold, done, cancelled), startDate, targetDate, budgetCents (blank = sum of lines), notes, vendorContactIds, archived |
| `budgetLine` | projectId, name, plannedCents, sort order |
| `commitment` | projectId, budgetLineId (optional), vendorContactId (optional), title, status (quoted, accepted, declined, cancelled), amountCents, parentId (a change order points at the commitment it changes; its amount may be negative), acceptedDate, notes |

Not entities in the first release: invoices, payments, milestones, project expenses. A payment is a Ledger transaction; a milestone is a task flagged `isMilestone`; an invoice is a note, a document later, or a "Pay invoice" task with a due date.

On other records (all optional, no migration):
- Transaction: `project?: { projectId, budgetLineId?, commitmentId? }`. Split: the same optional `project` on each split. A commitment implies its line unless a line is given.
- Task: `projectId?`, `isMilestone?`. Event: `projectId?`.

## Is a simple `projectId` enough?
- **For "how much has this project cost against its budget": yes.**
- **For the commitment scenarios (deposit, partial payments, what is still owed on this contract): no.** Without a link from a payment to a commitment, the app cannot say "$13,000 of $19,000 is paid." A line reference is also needed to show paid-per-line for purchases that have no contract.
- So: one small reference object on the transaction (project, optional line, optional commitment), as above. It sits on the transaction because a transaction is one record and edits to it sync cleanly. The alternatives are worse: a list of payments inside the commitment is edit-conflict prone and duplicates the Ledger; the `links` table has no integrity checks and costs extra reads; a tag carries no amounts.
- No index. Scan on the project page; revisit only if measured slow in a browser.

## Rules (all amounts in cents, spend shown positive; Ledger outflows are negative)
For each transaction piece from `projectAllocations` (transfers are never included):
- **Paid (actual)** = minus the sum of pieces for the project. A refund is a positive piece and reduces it.
- **Paid on commitment c** = its outflows minus its reversals and credits (never below zero).
- **Agreed** = sum of commitments with status accepted, including change orders. Declined, quoted and cancelled are excluded.
- **Left to pay on c** = max(0, amount of c minus paid on c). It counts work not yet invoiced as well as invoiced-unpaid; the label says so.
- **Overpaid on c** = max(0, paid on c minus amount of c). Shown as a warning, not subtracted.
- **Expected total** = Paid (actual) + sum of Left to pay.
- **Left in budget** = budget minus Expected total. Also shown: **Cash left** = budget minus Paid.
- **Not yet planned** = budget minus the sum of line plans (a warning if negative).
- **Line view:** planned; agreed (commitments on that line); paid (pieces with that line, directly or through their commitment); left to pay; over or under = planned minus (paid + left to pay). Pieces with no line go in a "No budget line" row.

## Edge cases
| # | Case | Rule |
|---|---|---|
| 1 | Quote not accepted | Status quoted. Shown as "Quotes waiting (not counted)". Competing quotes for one line get a notice. Accepting one does not touch the others; the owner marks them declined. |
| 2 | Accepted commitment | Counts as Agreed and as Left to pay until payments are tagged to it. |
| 3 | Invoice against an existing commitment | No new money, so no new record. If the invoice is more than the agreement, add a change order. Optional later: a "billed so far" figure. |
| 4 | Deposit or partial payment | A Ledger transaction tagged with the commitment. Left to pay falls by that amount. Expected total is unchanged. |
| 5 | Several payments on one commitment | Summed. Paying more than the agreement raises an "overpaid" warning that suggests a change order. |
| 6 | Payment as a Ledger transaction | The only way a payment exists. A payment not entered in Ledger is not counted. |
| 7 | Money coming back on a contract | **Amended 2026-11-05.** The owner must mark it **Reversal** (undoes a payment: Paid falls, the contract is owed again, Agreed unchanged) or **Credit** (cash back for a price reduction: Paid falls, and Agreed must fall by the same through a negative change order; otherwise the contract looks owed again and the dashboard flags it). Unmarked is refused. Money in with no contract (insurance, rebate) needs no mark and only lowers Paid. A credit applied to the balance has no transaction, only the change order. |
| 8 | Cancelled or revised | Revised: add a change order (keeps history, syncs safely). A direct edit of the amount is also allowed. Cancelled: status cancelled, Left to pay becomes zero; money already paid stays in Paid and is flagged "paid on a cancelled commitment" until refunded or re-assigned. |
| 9 | Transfers | Never project spending. The project field is hidden on transfers; converting or pairing a tagged transaction as a transfer clears it. A card purchase tagged to a project and the later card payment from checking (a transfer) therefore count once. |
| 10 | Tag after the fact | Allowed at any time, singly or in bulk. Totals are derived, so nothing needs correcting. A date outside the project's dates shows an information badge; dates do not exclude. |
| 11 | Split receipt | The split-level reference decides; the untagged part stays ordinary household spending. |
| 12 | Reimbursement (insurance, rebate) | A positive transaction tagged to the project; lowers Paid, like a refund. |
| 13 | Deleting | A project, line or commitment that has money attached is archived or cancelled, not deleted. An empty one can be deleted. A tagged transaction whose project is gone shows "(deleted project)" and can be re-tagged. |
| 14 | Monthly budget | Unchanged. The tagged transaction still counts in its category and month. Whether it should be excluded is an owner decision (O1). |

## Dashboard
Top row, in plain words, obligations and cash kept apart:
1. **Budget**
2. **Paid so far** (cash out)
3. **Agreed, not yet paid** (owed)
4. **Expected total** (paid + owed)
5. **Left in budget** (budget minus expected total), turning to "Over by" when negative
6. **Not yet planned** (budget minus line plans), shown only if not zero
7. Smaller: **Quotes waiting** (not counted)

One bar: Paid | Agreed unpaid | Left | Over. Table by line: Planned, Agreed, Paid, Left to pay, Over/under. Flags: over budget, line plans above budget, overpaid commitment, money paid on a cancelled commitment, tagged transactions outside the dates, old unanswered quotes. "Uncommitted budget" is useful per line (planned minus agreed) and appears as that column's hint, not as a headline.

# AI readiness (assignment section 4)

**Fit with what exists.** The Add box's `QuickAddDef` (`parse`, preview "Will add…", `commit`, optional undo) is already the right shape for a safe write: preview, user confirms, commit, undo. Registry hooks (`contributes.*`) are the right place for a future `assistantTools`. Everything here assumes a call goes through the same validated functions the screens use.

| When | Do | Why now |
|---|---|---|
| **Phase 0** | Finance changes as plain typed functions in `src/lib` with their own checks and no screen code (A3, later B6). Read answers as small pure functions that return plain data (`summariseProject`, `spendingSnapshot`). Keep the "one record per fact" rule. Put the Content-Security-Policy in (B5) so adding a provider means adding one host. Record the decisions in Deliverable 4. | Cheap now; expensive to retrofit into screen code later. |
| **During Projects** | Give each Projects action the same three parts as `QuickAddDef`: a check, a preview of exactly what changes, a commit that returns how to undo it. Mark which fields are money. Keep read functions returning only what a question needs. | The assistant can then use them with no new design. |
| **Wait for the AI phase** | The `assistantTools` registry hook; per-module and per-field sharing switches ("send amounts" off by default); a preview of the exact text being sent; the activity log (store as `moduleRecords` module `assistant`, kind `activity`, which gets backup and sync free, so no new table); provider choice; where the key lives; confirmation screens; rate limits. | These depend on choices not yet made. |

**Key security.** In a browser-only design the provider key sits in the browser, the same class of secret as the sync token: use a restricted key with a spend cap at the provider. A thin proxy (for example a small serverless function holding the key) keeps the key out of the browser, enforces data limits and can log centrally, at the cost of a service to run and a way to authenticate the browser. Decide at the AI phase; keep the call behind a single `aiTransport` function so the choice can change.

**Untrusted text.** Payee names from imported CSV files, notes and contact text could contain instructions aimed at a model. Tool results must be handed to the model as data, and every change an assistant proposes must go through the confirmation step.

**Undo.** Creates are undone by removing the created record (as the Add box does). Edits need the previous value saved with the activity entry.
