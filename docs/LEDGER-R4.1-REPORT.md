## A. Executive summary

**Records** (`#/records`) is one read-only page that lists every document link already saved in Home & Assets, Household Services and Bills & Subscriptions: what the document is called, which household item or arrangement it belongs to, where its record is, and two separate buttons, **Open document** (the saved web link, in a new tab) and **View record** (the record that holds it, such as "View appliance"). You can search it, narrow it to one module, and see a short list of **documentation gaps** (a stored warranty with no document linked). Search (Ctrl+K) now also finds document links, and "Records" is a link under the open module list.

It is a window, not a store. Nothing is copied, moved, uploaded or edited: the record in its own module stays the single source of truth, and a link is changed on that record. A household with no links gets a plain explanation and buttons to the three modules.

## B. Source coverage

Every module keeps references in the same shape, `{ label, url?, note? }`, but on different records. All of these are indexed:

| Module | Records that hold references | Opens (View record) |
|---|---|---|
| Home & Assets | the asset itself (property, area, system, appliance, vehicle, other); each stored warranty; each service-history entry | `/assets/<id>`, `?warranty=<id>`, `?service=<id>` (the same addresses Search already uses) |
| Household Services | each arrangement; each logged visit | `/services/a/<id>`, `/services/v/<id>` |
| Bills & Subscriptions | each bill or subscription | `/bills/o/<id>` |

**Not indexed, deliberately** (no stored document reference exists or the relationship is not reliable): the shared Attachment stub (a description-only entity with no UI and no use; not touched); an asset's old single warranty date and note (they hold no document; the asset's own list is indexed); insurance policies in Finance's Protection area (no reference list; R0 says link, not duplicate); family identity documents (out of scope); Projects, Contacts and Family (no reference list). Review of the "Records may include a route to the insurance area" idea: not added, because Protection has no document fields and a bare link would imply there is something to find.

**Shapes are not identical in every module, and the adapter respects that:** Bills and Services allow 20 references with a 120-character label and 500-character note; Home & Assets allows 20, label 80, note 200, link 500. Services and Bills store the address in `url` exactly as Home & Assets does, but each module's save form validates with its own copy of the same `isSafeUrl` (now one shared function). The adapter does not re-validate length; it only classifies the address.

## C. Architecture

- **Contract (`src/core/documentRefs.ts`, pure).** `DocumentRef` (a common row), `DocumentGap`, `DocumentSource { label, read({ today }) }`, `makeRefs(owner, record.refs)` (never throws; skips an unnamed reference; carries an address only when `isSafeUrl` accepts it), and the pure helpers `filterRefs`, `sortRefs`, `refMatches`, `expiryState`, `refSearchLine`, `recordsPath`.
- **Registry.** One small optional hook, `contributes.documentRefs`, and `allDocumentSources()` (`registry.ts`). It is documented in `docs/module-hooks.md`. It sits beside `records` (record linking) without reusing it: that hook describes one record to link to; this one lists references inside records.
- **Module adapters (lazy).** `assets/docRefs.ts`, `services/docRefs.ts`, `bills/docRefs.ts`. Each calls its module's own loaders (`loadAssets`, `loadWarranties`, `loadServices`; `loadArrangements`, `loadVisits`; Bills reads its obligation rows with `asObligation` and skips the lifecycle and billing-period reads that `loadObligations` also does, because this index does not need them). Each module's `index.tsx` registers `read: (ctx) => import('./docRefs')...`, so nothing is downloaded or read at start-up. A test pins that no module imports its adapter eagerly.
- **Identity.** `id` = `<module>:<kind>:<record id>#<position>` (for example `assets:warranty:12#0`). The same label or the same web address on two records stays two rows; two references on one record differ by position. The position lasts only until that record's list is edited, which is why Search carries the id only for the moment between clicking and opening the page.
- **Loader (`src/shell/recordsIndex.ts`).** `loadDocumentIndex(today)` asks every source in parallel; a source that throws or rejects is recorded as not read and the others still list. The result says `complete: false` when any failed.
- **Screen (`src/shell/RecordsPage.tsx`, `records.css`).** A shell route like Settings and Quick Answers: no twelfth module, nothing on Today, loaded on demand (`lazyModule`, preload on a `#/records` address). `SHELL_PATHS` lists `/records` so the Ledger prefix never rewrites it.
- **Search.** A "Documents" group (kind "Document") built in `SearchDialog` from `searchDocuments`. The three modules are read once, on the first typed word, cached for the life of the open dialog and dropped on close. R3.2 Quick Answers, the Actions list, arrow keys and Enter behave as before (the Documents group is ranked by its best match like every module group, and sits below Actions and Answers, so no existing position moves).
- **Loading cost.** The Records page and Search read three module record sets; no Finance transaction table is touched. Entry chunk 755.49 kB raw / 237.14 kB gzip (R3.2: 752.58 / 236.07; +2.9 kB / +1.1 kB for the hook, the Search group, the menu link and the route); the Records page is its own 9.6 kB chunk (3.2 kB CSS) and the three adapters are 0.7 to 2.3 kB each.

## D. Records and gaps

**Reading the list.** Grouped by module (when "All records" is chosen), then by the item's name, record, document name. Each row: document label (bold); "Belongs to **Dishwasher** · Warranty: Manufacturer warranty"; module and where it sits (Kitchen, the visit date, the provider); the site name of the link (not the whole address); a note; "Warranty ends ..." with **Expiring soon** (within 60 days, the same as Home & Assets) or **Expired**; "Link needs review"; "No web link saved". Nothing moves to the top for being close to expiring (the list does not jump around); the chip and the "Warranty ending soon or ended" filter carry it.

**Search (in the page).** Every typed word must appear in the document name, the item's name, the record kind or name, where it sits or the module name. It does **not** search notes, addresses or the inside of any file, and says nothing like that. Filters: All records and one button per module (with counts; a module that could not be read is shown disabled as "not read"), "Warranty ending soon or ended" (only shown when some reference has a real end date), "Link needs review" (only shown when one exists). No sort control: the single stable order is the clear value; an extra sort would add little at this size.

**Document kind.** Not stored anywhere, so there is no "type" filter and nothing is guessed from labels such as "manual" or "invoice". "Unclassified" is not shown because every reference is unclassified.

**Expiration.** Only a stored warranty's own end date is attached to its documents. Not used: purchase and service dates; an asset's old single warranty date; Services renewal and notice dates (they belong to the agreement, not to one saved link); Bills renewal dates (a recorded lifecycle fact can supersede `terms.renewalDate`, so copying one could show a stale date).

**Documentation gaps (warranty only).** A gap is listed only when all of these hold: a **stored** warranty record exists (it exists to hold documents); it has no reference at all (a reference with a name but no web link counts as "something is recorded"); the asset is not archived or sold, disposed of or replaced; and the warranty has no end date or ends today or later. Not listed: an ended warranty, anything on an archived or retired asset, the asset's old single warranty date (its papers may be on the asset), and anything in Services or Bills (no structure says a document must exist). Words: "No document linked" chip and "No warranty document is linked."; the note says a missing link is not proof the household lacks the paper. The test pins that "missing", "lost", "unprotected" and "not covered" never appear. Selecting a gap goes to the existing record (the warranty is highlighted on the asset page), where the normal document form applies; Records has no form of its own. On a phone the gap list starts folded to one line so it does not push the records off the first screen; on a computer it starts open (first three, then "Show all").

## E. Security and privacy

- **Links.** Only an absolute `http:` or `https:` address (the one shared `isSafeUrl`, `src/lib/safeUrl.ts`) becomes an Open document link. `javascript:`, `data:`, `ftp:`, a relative path and a bare word become **Link needs review**: no link, the address is not carried in the row at all (a test searches the serialized row), and the owner is sent to the record. Nothing is rewritten, deleted or repaired. No link is fetched, so "valid" never means "still there"; the page says it cannot tell whether a link still works.
- **Display.** Labels, owners, notes and sites are React text (no `dangerouslySetInnerHTML`; a source scan test checks all six new files). Open document is `target="_blank" rel="noopener noreferrer"`. Only the site name is shown, never the whole address, and not in Search or in the web address of a Records page.
- **Sensitive fields.** Asset serial number, plate and address are never read (the adapter uses the asset's name and its parent path, the same safe path Search uses); a test puts a serial and an address on the invented asset and finds neither in any row.
- **Hide amounts.** An amount typed into a label, owner or note is masked when Hide amounts is on (checked in the browser: `Receipt $1,250.00` showed as `Receipt $••••`, 0 visible dollar amounts on the page). Search results are not masked, as for every other module's results today.
- **Read only.** No new table, migration, file storage, backup or sync change, backend, dependency or network call. A test hashes every database table, runs all three readers, the loader and the Search function, and shows nothing changed. Another test scans the six new files for any write, `fetch`, storage or HTML injection call.
- **No new third party.** Document addresses go nowhere except the user's own click opening them in a new tab.

## H. Judgment calls (please review)

1. **A shell page, not a module.** `#/records` is like Settings and Quick Answers: no twelfth module, nothing on Today. It is reached from a **Records** link under the open module list (computer and phone), from Search, and from the module empty states.
2. **Gaps start at the top (folded on a phone).** The brief lists gaps after the records on a computer; I put them above so they are not buried under a long list. If you prefer them last, it is a move of one block.
3. **Only warranty gaps, only stored warranty records.** An asset's old single warranty date is not flagged (its document could be on the asset). Ended warranties and archived or retired assets are not flagged (nobody can act on them). The cost is that a lapsed warranty with no document is invisible here.
4. **A name with no web link is still "a document reference".** "Paper copy in the kitchen drawer" with no address is listed ("No web link saved") and stops a gap from being reported.
5. **Dates: warranty end dates only.** Renewal, notice, trial and service dates were left out on purpose (section D). A document-level expiration is what the optional field below would add.
6. **Open document vs View record.** Two buttons per row, one filled and one outlined, with different words; "View record" reads "View appliance", "View arrangement", "View bill" and so on, so it names what you are going to.
7. **Search opens one reference, not the owner or the file.** A Document result opens the Records screen showing that one reference with both buttons, so one click never sends someone to an external site unseen, and the record is one more click. It carries only the reference id in the address.
8. **Position-based ids.** Two references are told apart by owner and position, not by content; editing a record's list can change an id (no data depends on it).
9. **No sort control, no "type" filter, no "Unclassified".** Document kind is not stored; guessing from labels was refused.
10. **Hide amounts** applies on Records but not in the Search dialog, matching every other module's Search rows today.
11. **Bills read directly.** The Bills adapter uses `asObligation` on the obligation rows, not `loadObligations`, to avoid the lifecycle reads. It shows a bill's own status ("Ended", "Paused") but no dates.
12. **Future optional metadata (not built, owner decision).** (a) *Document kind* (warranty, receipt, manual, contract, insurance, other) per reference, which would unlock a real type filter and a better gap rule; (b) *Document end date* per reference (separate from a warranty's end), for policies and contracts; (c) *"Paper copy at..."* text per reference, which would serve the family's "where is it" need without storing a file. Each is an optional field on the existing reference shape in **three modules' save forms**, so it is a change to three editing workflows plus sync of an unknown key through older builds; I recommend deciding after you have used the index for a while. None is built and no field, migration or sync change was made.
13. **UI tracker row S-25** is BLT with only `L`, `375` and `Func` recorded.
14. **Screenshots are kept outside the repository**, as in earlier phases.

**NOT built:** file uploads or storage of any kind; previews; folders or tags; OCR or AI of any kind; sharing; R4.2 Family Lenses; R4.3 calendar export; new insurance or identity-document records; a Today card; editing a link from Records; automatic cleanup of a bad link; any new field, table, migration, dependency, backup or sync change; a Protection (insurance) route; a document-kind filter; a sort control.
