# Module hooks for Today, search and quick-add

Added in Phase 3. These sit next to the due-provider contract (`docs/due-provider.md`) in `ModuleDef.contributes`. **`todayCards` is in use
since Part B** (the Today module and Ledger each offer cards); `searchSource` is in use since Part C (Ledger, Calendar, Tasks and Today each offer one); `quickAdd` is in use since Part D (Tasks, Calendar and Ledger each offer destinations). A module that
offers none of them behaves exactly as before. The types live in `src/core/registry.ts`.

```ts
contributes: {
  todayCards?: TodayCardDef[];
  searchSource?: SearchSource;
  quickAdd?: QuickAddDef;
  txnReferences?: TxnReferenceProvider; // ST-S2: see "txnReferences" below
  contactReferences?: ContactReferenceProvider; // C2: see "contactReferences" below
}
```

## `todayCards`: a card on the Today screen

| Field | Meaning |
|---|---|
| `id` | Permanent, and must start with the module id (`ledger.alerts`). Saved layouts refer to it. A wrong or repeated id is rejected when the app starts. |
| `title` | Card heading, also used in the edit-layout list. |
| `defaultWidth` | `'half'` or `'full'` on desktop (phones are one column). |
| `priority` | Position in the default layout; lower comes first. |
| `hideWhenEmpty` | Hide the card (rather than show an empty state) when it reports it has nothing. |
| `Component` | Receives `{ today, hideAmounts, reportEmpty }`. `today` changes at midnight. A card that shows money must honour `hideAmounts`. Call `reportEmpty(true)` when there is nothing to show. |

Dated things (events, tasks, bills) should normally come through the due provider, not a card. Use a card for what is not date-based
(alerts, a cash outlook, a count).

`allTodayCards()` returns every card in default order.

### How Today uses them (Part B)

- **Cards in use.** Today module: `today.agenda`, `today.reminders`, `today.overdue`, `today.upcoming` (`src/modules/today/cards.tsx`). Ledger:
  `ledger.attention` and `ledger.cash` (`src/modules/ledger/todayCards.tsx`). Projects: `projects.attention`. Home & Assets (H5): `assets.attention` (`src/modules/assets/todayCards.tsx`), a counts-only card (no asset names, amounts or private details) that never lists the maintenance tasks themselves, because Tasks already put those on Today; it hides itself when nothing needs attention and reads the same `loadOverview` the Overview page uses.
- **One aggregation for dated items.** `TodayDataProvider` (`src/modules/today/TodayData.tsx`) calls the Calendar's data hook once (your events plus
  every due provider, covering the overdue window, today and the look-ahead). The four Today cards read that list through `useTodayData()` and
  only slice it (`src/modules/today/logic.ts`, pure and tested). A new module's tasks or bills show up with no card of its own.
- **Sharing a query between cards.** `useSharedLive(key, loader)` (`src/core/sharedLive.ts`) runs one live database query per key and shares it. The
  cash forecast feeds both Ledger's alerts and the cash outlook, so it is worked out once. The key must name everything the query depends on.
- **Hide amounts.** A card that shows money must honour `hideAmounts`. Text that may contain money (an alert title, a bill name) goes through
  `maskAmounts()` (`logic.ts`).
- **Layout.** `src/modules/today/layout.ts`: per device, saved under `today.layout.v1` (in the backup preference list). Cards come from the registry,
  so a new card appears at the end by itself and a card that disappears is ignored.
- **Failing cards.** Each card is wrapped in an error boundary, so one card breaking never blanks the screen.
- **"N older items".** A due provider can add `olderThan(cutoff, today)` (see `docs/due-provider.md`).

## `searchSource`: what global search can find

`search(query, limit)` returns `SearchResult[]` (`id`, `title`, `subtitle?`, `kind` badge text, `score?`, and either `path`, a full
address such as `/tasks`, or `open()` for hits that need more than navigation). Results are grouped by module under `group` (default: the
module name). A linear scan is fine; do not build an index unless a measurement says it is slow. `allSearchSources()` lists them.

### How search uses them (Part C)

- **Every module answers, the dialog groups.** `src/shell/SearchDialog.tsx` waits 90 ms after typing stops, asks every source in parallel (a source that
  throws is left out), and `groupResults()` (`src/shell/searchGroups.ts`) orders the groups by their best hit. Hits open by `path` (a full address, query
  string allowed) or `open()`.
- **Optional `start()`.** Called when the dialog opens; it returns a function called when it closes. Ledger uses it to keep a live in-memory snapshot of
  its tables (reading 20,000 transactions out of the database cost about 90 ms per keystroke; scanning them costs about 8 ms). Nothing is stored or indexed.
- **Sources in use.** Ledger (`modules/ledger/searchSource.ts`: pages, accounts, investments, holdings, loans, scenarios, scheduled items, transactions), Calendar
  (`modules/calendar/searchSource.ts`: the page and events by title, notes, location), Tasks (`modules/tasks/searchSource.ts`: the page, tasks by title, notes and
  checklist, plus the shared tags and contacts), Today (`modules/today/searchSource.ts`: the page). The matching code in each is pure and tested.
- **Deep links these rely on.** `#/tasks?task=<id>` (opens a task), `#/tasks?v=all&tag=<id>` and `&contact=<id>` (filter), `#/calendar?v=agenda&d=<date>&open=<key>`
  (opens an event), `#/calendar?new=1` (blank event), `#/ledger/scheduled?rule=<id>` (edit a scheduled item).

## `quickAdd`: what the global add box can create

`contributes.quickAdd` is one destination or a list. Each one is a button in the Add box.

| Field | Meaning |
|---|---|
| `id`, `label` | Permanent id and the chooser text ("Task"). |
| `prefix`, `aliases?` | Typed shortcuts: text starting with one of them and a space picks this destination (`t `, `task `, `task: `). Two destinations that share a prefix or alias (any case), or an id, are rejected at start-up. |
| `parse(text, {plain})` | Understands the text after the shortcut and returns a `QuickAddPreview` (`summary`, `fields`, opaque `payload`), or `null`. The box always shows it as "Will add: ..." before saving. `plain` turns the shorthand off (the whole text is the title). |
| `commit(preview)` | Creates the record, only after the user has seen the preview and pressed Add. May return a function that undoes it (shown as Undo in the toast). |
| `start()` | Optional. Called when the box opens, returns a stop function. Lets the synchronous `parse` know existing calendars, lists and tags (so the preview can say "(new)"). |
| `Form` | Optional. For a destination that is a form, not a line of text (Ledger's transaction): the box shows this component instead of a preview. |
| `open({navigate})` | Optional. For a destination that is another screen's own form (Ledger's scheduled payment): the box shows a button that calls this. |

The box never guesses a destination: no shortcut and no choice means it asks. `allQuickAdds()` lists the destinations; the pure routing is `routeQuickAdd()` in `src/core/quickAddRoute.ts`.

### How the Add box uses them (Part D)

- `src/shell/AddBox.tsx` is the one box (the "+" / Add button, `openAddBox({dest, text})` in `core/globalEvents.ts`, and the old `ledger:add-transaction` event all open it). Choices read Task, Event, Transaction, Scheduled payment; destinations from new modules follow.
- **Destinations in use.** Tasks: `task` (`modules/tasks/quickAddDef.ts`, the Tasks bar's own parser). Calendar: `event` (`modules/calendar/quickAddDef.ts`, parser in `quickEvent.ts`). Ledger: `transaction` (the quick transaction form) and `scheduled` (opens Ledger Scheduled) in `modules/ledger/quickAddDef.tsx`.
- **Events from anywhere:** `requestEvent({title, date})` (`core/eventBridge.ts`) opens the box on Event with that text, like `requestTask` for tasks.
- **Event words:** the same date, priority, tag and repeat words as the Tasks bar (it reuses that parser), plus time ranges (`3-4pm`), `@calendar`. No date = today, no time = all-day, one time = one hour.

## `txnReferences`: which of my records point at a Finance transaction (ST-S2)

Added in Stabilization ST-S2 (DI-02). A module that holds references to Finance transactions contributes a **read-only** reader, so Finance can say what depends on a payment before it is deleted **without importing any household module**. Types and the reader live in `src/core/txnDependents.ts`; the registry exposes `allTxnReferenceProviders()`.

```ts
contributes: { txnReferences?: { label: string; find(ctx: { ids: number[]; txns: Map<number, Txn>; d: FinanceDB }): Promise<TxnDependent[]> } }
```

| Rule | Meaning |
|---|---|
| Read only | Nothing is written, deleted or repaired. A guard test (`src/lib/txnDeletionGuards.test.ts`) rejects table writes, `.transaction(`, logging, storage and network calls in the readers. |
| Tables | Read only `txns` and `moduleRecords` (Ledger's own reader also reads `recurring` and `recurringLog`). The delete runs the readers again inside one database transaction scoped to those four tables; a reader that touches another table makes the delete refuse (safe) until the scope is widened in `src/lib/txnDeletion.ts`. |
| By id | A record points at a transaction by id or it does not. Never match by payee, amount or date. |
| One row per record | Two stored references to one record are one dependent (`recordId` is unique within the module). `scope` is `whole` or `part` (with `parts`). |
| `standing` | `current` (in force), `stale` (already needs review, judged with the shared `resolveRef`), `historical` (kept as history: replaced, rejected, or a saved entry this version cannot read). `evidence` is true only for `current` records that count the payment. |
| No money | Titles and notes never contain an amount. |
| Failure | Throw. The caller reports "could not check" and refuses to delete; it never says "nothing depends on this". No readers registered is also "could not check". |

Registered by Bills, Household Services, Home & Assets, Projects (the tag sits on the transaction itself) and Ledger (scheduled-payment history). A new module that stores a Finance reference must add one, with a test that its reader finds it.

`searchSource` note (ST-S2, NV-01): Household finances contributes a **page-only** search source (no records, no figures), the same pattern as Today.

## `contactReferences`: which of my records point at a shared Contact (Contacts C2)

Added in Contacts & Relationships C2. A module that stores a shared Contact id contributes a **read-only** reader, so the Contacts screens can show real, named, linkable records ("Task: Book the dentist") **without importing any household module**. Types, the shared reader and the grouping words live in `src/core/contactReferences.ts`; the registry exposes `allContactReferenceProviders()`. It is layer 2 of the plan in the C0 document; layer 1 (`src/core/contactUsage.ts`) is the field-blind numeric scan.

```ts
contributes: { contactReferences?: { label: string; find(ctx: { ids: ReadonlySet<number>; d: FinanceDB; today: string }): Promise<ContactReference[]> } }
```

| Rule | Meaning |
|---|---|
| Read only | Nothing is written, created, repaired or re-stamped. Guard tests reject table writes, `.transaction(`, storage, network and Finance reads in the reader files, and a hook on every table proves no write fires. |
| Tables | Only `moduleRecords` (and `contacts` for a name). Never a Finance table. |
| By id | A record names a Contact by its stored id or it does not. Never by a matching name, title, payee, amount or provider-name snapshot. |
| Each row on its own | Use `readRows(d, module, kind, asX)`: a damaged row is skipped and cannot stop the module's list. (Tasks' and the Calendar's own loaders throw on a row whose data is null.) |
| One reference per (record, role) | `role` is a short code (`person`, `vendor`, `provider`, `extra`, `member`, `important`). `facet` (member, important, provider, project) feeds the directory filters and comes only from the stored relationship. |
| Plain words | `title` is the record's name (never an amount, note or contact detail); `relation` says how it uses the Contact; `href` is a path inside Ledger written with the owning module's own deep-link format (it must start with `/`); `inactive` marks a finished, archived or ended record (still listed, shown quietly). |
| Failure | Throw. The caller says "could not check" and never "nothing found". An item the shared reader cannot understand is dropped and makes the result unverified. |

Registered by Family (member, important contact), Calendar (event `contactIds`), Tasks (`contactIds`), Projects (`vendorContactIds`, commitment `vendorContactId`), Home & Assets (asset `contacts`, service and warranty `providerContactId`), Household Services (arrangement `providerContactId` and `extraContactIds`, visit `providerContactId`) and Bills & Subscriptions (`providerContactId`). Contacts registers none (it owns no records). A module that adds a Contact field must add or extend its reader; `unlistedMentions()` shows the gap on the Contact page until it does. **Removal** (`src/core/contactRemoval.ts`) never relies on these readers alone: it needs the complete layer-1 scan and the older text rule to find nothing as well, and any reader that cannot run blocks it.

## Family's search source and Add-box destinations (Family Management F5)

Family registers one `searchSource` (group "Family") and two `quickAdd` destinations. No new table, link type, Calendar layer, Today card or dependency. Files: `modules/family/searchSource.ts`, `quickAddDef.ts`, `useAddIntent.ts`.

- **Search.** Hits are `Family member` (id `family-member:<id>`, active or past, opens `/family/m/<id>`), `Family birthday` (`family-birthday:<member id>`, active members, one per Contact, month and day only, shown only when the typed words are about the date) and `Family date` (`family-date:<record id>`, active dates, opens the member it names or `/family/dates`), plus the two Family pages. The Contact is reduced to its NAME before the pure `searchFamilyData` sees it: phone, email, Contact notes, a member's private note, birth years and anniversary start years are never searched or shown. A member whose Contact is gone, an unreadable record and an archived date are not offered. Two members with one name stay two hits; their subtitles add "Added <date>" so they can be told apart. Read-only (a test snapshots every table; the write-trap test in `lib/readOnlyTrap.test.ts` runs every registered source).
- **Add box.** `family-member` (prefix `fam`, alias `family`) and `family-date` (prefix `fd`, alias `famdate`) are `open` destinations with no `parse`, `commit` or `Form`: they go to `#/family?add=member` and `#/family/dates?add=date`, where the page opens its OWN existing form once (`useAddIntent`) and removes the address word (replace, like the Calendar's `new=1`). The Add box saves nothing for Family, so the Contact identity rules, Spouse, the opt-in "This is me", Cancel and the F2 date rules are the forms' own.
- **`QuickAddDef.openCopy` (new, optional).** `{ what, where, button }` words for an `open` destination ("a family member" / the sentence about where it is set up / the button text). Without it the box says "a <label>" and "Open the form". Ledger's Scheduled payment states its own words, so its screen is unchanged.

## Loading a module's screens on demand (ST-S4, PF-01)

A module is two things, and only one of them waits until the module is opened.

| Part | When it loads | Where it lives |
|---|---|---|
| **Registration**: `ModuleDef` and everything in `contributes` (Today cards, search source, Add-box destinations, Calendar due provider, record source, `createFromEvent`, `txnReferences`), the address list `routePaths`, the icon and name | with the first download, always | `src/modules/<id>/index.tsx` and the files it imports |
| **Screens**: the module's `<X>Module.tsx` and every page under it | the first time the module (or an address inside it) is opened | a separate file per module, fetched by `import()` |

Why: Today, search, the Add box, the Calendar and Finance's delete check all need a module's contributions before anyone opens it, so those can never wait. Only the screens can. The registry contract is unchanged: `ModuleDef.Component` is still an ordinary `ComponentType`.

**To add a module:**
1. Put the address prefix in `src/modules/bases.ts` (or keep it in a small file the registration may import), never in the `<X>Module.tsx` file.
2. In `index.tsx`: `Component: lazyModule(() => import('./XModule'))` (`src/core/lazyModule.ts`). Never `import XModule from './XModule'` there, or anywhere the first download reaches; `src/modules/lazyBoundary.test.ts` walks the static imports from `main.tsx` and fails if a lazy module's screens (or Settings) come back in.
3. `routePaths` must not be derived from the page components (Ledger keeps its list in `ledger/routePaths.ts`, and a test pins that it equals the routes its screens serve).
4. Put the module's stylesheet in `src/modules/moduleStyles.ts` (the order there is the cascade order). Styles are NOT split: the whole sheet is 19 KB compressed and Today's cards use classes from several modules.
5. Nothing in a module's screens may register anything at import time (today only `registerModules()` in `App.tsx` registers); the screens file can be loaded late or not at all.

**While a module's screens load.** `App.tsx` wraps each module in `ModuleLoadBoundary` (`src/shell/ModuleLoader.tsx`). The page area is an empty `main` landmark with a marker (`data-module-loading`); "Loading <name>…" is said only if the wait passes 150 ms. The route announcer waits for the marker to go (up to ten seconds) before reading the heading, so the page title and the spoken page name are the real ones. If the file cannot be fetched (offline and not saved, or an update removed it) the module shows "<name> did not load" with **Try again** and **Reload Ledger**; the top bar, search and Add box keep working, and nothing stored changes. A real bug in a screen is not caught: it fails exactly as it did before.

**Why not `React.lazy`/`Suspense`.** React keeps a revealed loading state for about 0.3 s, which made opening a saved module take 0.3 s instead of a few milliseconds. `lazyModule` has its own small state instead, asks for the file once however it is started, shows the screens in the first pass once the file is here, and forgets a failure so Try again really asks again.

**Start-up preload.** `main.tsx` starts downloading the module named in the address (or the landing module from Settings > General) while the database opens, and the first draw waits for it for at most 400 ms (`preloadForAddress` in `App.tsx`).

**Offline.** The service worker (`public/sw.js`) saves every built script and style at install, so a module opens offline even if it was never opened before going offline. The build writes the file list and a build fingerprint into `dist/sw.js` (`serviceWorkerBuild` in `vite.config.ts`, `src/swBuild.ts`); nothing is typed by hand. Each build has its own cache (`ledger-<build>`); the build before it is kept for tabs that are still open, and older ones are removed. Only caches this app made are touched. See `docs/LEDGER-STABILIZATION-ST-S4-REPORT-2026-11-08.md`.

## The shell around them (also Part A)

- **Search and the Add button belong to the whole app.** `src/shell/GlobalFrame.tsx` owns the search dialog and its shortcuts
  (Ctrl/Cmd+K, or `/` when not typing); `src/core/ModuleBar.tsx` shows the Search and Add buttons and mounts the single quick-add
  (`src/shell/QuickAdd.tsx`). Anything can open search with `openSearch()` (`src/core/globalEvents.ts`) and the transaction form with
  `openAddTransaction()` (the `ledger:add-transaction` event still works)..
- **Bottom-of-phone rule.** `ModuleDef.hasTabBar` says whether a module draws its own bottom tab bar (only Ledger). `GlobalFrame` sets
  `data-tabbar` on the page; the CSS variable `--tab-h` is then the tab bar's height (57 px) or 0. The round "+" button, the toasts and
  the page's bottom padding are all placed relative to `--tab-h`, so they sit at the screen edge in Calendar, Tasks and Today and above
  the tab bar in Ledger. A new module with a bottom bar sets `hasTabBar: true`; one without needs nothing.
- **Landing module.** `src/core/shellSettings.ts` keeps one `settings` row (`shellSettings`, so it is in backups and syncs):
  `landing` is `'today'` (default), `'last'`, or a module id. `resolveLanding` never returns a module that is not registered. Set it in
  Settings > General.
- **A date that follows midnight.** `useToday()` (`src/ui/useToday.ts`) returns today's date and updates it when the day changes
  (checked every 30 s and when the page becomes visible). Use it instead of `todayISO()` in anything that stays on screen.

## Home & Assets record ids (H1)

`modules/assets/records.ts` registers `contributes.records` with text ids `asset:<n>` and `service:<n>` (H2; `warranty:<n>` comes in H4). A Task or Calendar event links to an asset through the shared Links (type `about`) from its own "Link a record" box. Search group "Home & Assets" (serial and plate match by prefix, 4+ characters, and are never shown); Add box destination `asset` (prefix `a`, aliases `asset`, `item`; "Name in Exact Asset Name"). H2 adds service records: search by title and notes (opens `#/assets/<id>?service=<id>`), and the Add box destination `service` (prefix `svc`, aliases `service`, `repair`; "Work on Exact Asset Name $amount date", refuses with a reason when unclear).

`modules/services/records.ts` (Household Services, S1) registers `contributes.records` with text ids `arrangement:<n>`; labels are the title, provider name and status only (never phone, email, notes, links or amounts). A Task is linked to its arrangement through the shared Links (task -> arrangement, type `about`), and an arrangement to an asset through type `serves` (arrangement -> `assets:asset:<n>`, created from Household Services only). The Task carries two markers in its carried-through unknown fields, `servicesArrangement` and `servicesOccurrence` (the cadence date it stands for); the Tasks editor preserves them (tested). Search group "Household Services" (arrangement title and provider name; deep links `#/services/a/<id>` and `#/services/providers/<contact>`); Add box destination `household-service` (prefix `hs`, alias `household`; preview first, Undo removes it). **S2 additions:** a visit record (module `services`, kind `visit`, ids `visit:<n>`, described by title and provider name only) is also returned by the records source and Search (title and provider name only; notes, amounts, links and contact details are never searched or shown). The Task carries a third optional marker, `servicesPurpose: 'book'` (a booking reminder; no marker means a visit Task). A visit links to assets with type `serves` (visit -> `assets:asset:<n>`). Today card `services.attention` (`modules/services/todayCards.tsx`): counts only, `hideWhenEmpty`, read-only, from the same reader as the overview. Add box: `hs visit <what> with <provider> [date] [$amount]` is a one-off visit. No Calendar layer in S1 to S3.

**S4 additions (Household Services, cross-module workflows and contract dates).**
- **Link types** (shared Links, no new table): `serves` (arrangement or visit to `assets:asset:<n>`, unchanged); **`recorded-as`** (`visit:<n>` to `assets:service:<n>`; the handoff identity and duplicate guard, one per visit and asset; written in the same transaction as the Home & Assets service record, `modules/services/handoff.ts`); **`involves`** (`arrangement:<n>` or `visit:<n>` to a Project, whose id is a plain number; information only, `modules/services/projectLinks.ts`). Deleting either end already unlinks cleanly; nothing in S4 reads or writes Project money or Finance.
- **Due provider and Calendar layer:** `contributes.dueProvider` = `servicesDueProvider` (id `services`, layer "Household Services", `modules/services/dueProvider.ts`). The sixth built-in Calendar layer has the fixed id **`9_000_000_000_000_106`** (`SERVICES_ID` in `modules/calendar/model.ts`; ids `..._101` to `..._105` are Personal, Finance, Tasks, Projects, Home & Assets), seeded by `ensureCalendarSeed`. One read-only marker per `renewalDate` and per `noticeByDate` of every arrangement that is not ended (a paused one still shows them): ids `services:<renewal|notice>-<arrangement id>:<date>`, titles "Renewal: <arrangement title>" and "Notice deadline: <arrangement title>", nothing stored, no Task or event, title only. **Expected visits (S4 pre-commit correction):** the same layer also shows every expected occurrence of an ACTIVE arrangement with a fixed schedule over a rolling 12-month horizon (`modules/services/plannedVisits.ts`): ids `services:visit-<arrangement id>:<date>` (cannot collide with the two above), title as the visit Task ("House cleaning: Rosa's Cleaning"), `time` = the arrangement's visit time (else all day), priority low, status always `open`, no actions. Dates come from the arrangement's cadence through the existing `cadenceBetween` (no new recurrence engine). **Contract with the Tasks layer:** the Tasks provider is unchanged and shows only the ONE open visit Task (it does not expand repeats); the Services layer starts strictly AFTER that Task's date and after the date it stands for, after any finished visit, and never before today, so no visit appears twice and a moved visit does not shift later dates. **Horizon:** from the `today` the Calendar passes in through the same day-of-month 12 calendar months later, both ends included, clamped to the month length (moves with the clock, nothing stored). Paused, ended, on-demand, "after each visit" and damaged schedules produce none. A future one-off skip or cancellation is not stored anywhere, so it cannot be removed in advance.
- **Today card `services.attention`** now also gets counts of renewal dates and notice deadlines from today through 30 days ahead (`attentionCounts(snapshot, today)`; the same `contractDeadlines` the Calendar uses): "N agreement notice deadline(s) in the next 30 days" and "N renewal date(s) in the next 30 days". Counts only.
- **Fields:** arrangement `renewalDate`, `noticeByDate` (`YYYY-MM-DD`, stored only when set; carried through by older builds). Undo (`undo.ts`) gained an additive `linkOps` (links added and removed) for Move to replacement and Project links; the sealed-state guard is unchanged.
- **Home & Assets touch points** (small, bounded): the asset page card `AssetServicesCard`, `ServiceForm` handoff mode and `AssetWork` `?fromVisit=<visit id>` (ids only in the address), the source chip on a service entry, the delete preview sentence (`planAssetDeletion` returns `serviceArrangements` and `serviceVisits`), and `insertService` exported from `serviceData.ts`.

**S5 additions (Household Services, Overview, household spending and insights).** No new table, link type, Calendar layer, Today card, search source or dependency. What changed:
- **One shared reader** (`modules/services/servicesOverview.ts`): `loadServicesOverview(period, today)` reads the Services snapshot (with its live links, one `links` read), the Home & Assets service records and the Finance transactions any payment reference points at (one bulk read), then hands them to the pure `buildServicesOverview`. It asks the code that already decides each thing: `buildOverview` (views.ts; the Today counts come from it), `contractDeadlines` (Calendar and Today), `plannedVisitDates` (Calendar), `servicesSpend` / `expectedWindow` (S3), `householdSpend` (below) and `buildInsights`. Nothing is stored or written; a test pins that repeated loads change no row.
- **`householdSpend(input, lookup, period)`** (`modules/services/householdSpend.ts`, pure): the deduplicated union of Household Services and Home & Assets recorded payments. It reuses H3's `spend()`, `resolveRef` and `pieceKey` unchanged and S4's `recorded-as` links (`pairsFromLinks`). Claims end as `included`, `merged`, `covered` or `excluded`; the included claims add up to the total, and `reconciliation` explains the difference from the two module totals claim by claim (overlap counted in both, parts covered by a whole in the other module, typed amounts on linked jobs). It never reads Project money (it only counts, for context, pieces Finance also tags to a Project).
- **`insights.ts`** (pure, deterministic, no model): trend against the comparable prior period, the 12-month estimate (kept apart from recorded money), unusual cost (needs 3 other reliable visits and a stable usual price), long gap, repeated skips or cancellations, dates that keep moving, optional unrecorded maintenance. `providerBreakdown` attributes spending to a provider only when unambiguous. `periods.ts` defines the periods and their prior periods.
- **Today** keeps its own light, count-only card (`attentionCounts` and `attentionLines` are unchanged); the Overview's Needs attention uses the same functions for the categories they share. S5 adds three Overview-only conditions (stale Finance references, duplicate handoffs, typed-amount notes) that are not on Today, because they need a Finance read that Today deliberately avoids.
- **Public-safe words:** Overview text carries titles, dates and counts; money comes only through a money function so Hide Amounts masks it; no phone, email, notes, links or typed amounts.

**Bills & Subscriptions additions (B1: registry, previews and figures; B2: billing-period facts, Tasks, Calendar layer, Today card).** Module `bills` (route `#/bills`; `#/bills/list`, `#/bills/upcoming`, `#/bills/review`, `#/bills/o/<id>`), records in `moduleRecords` (kind `obligation` and, from B2, kind `cycle`). Only `cycleData.ts` (record, edit, remove) and `cycleRepair.ts` (repairs and the period move) write them. Two devices adding facts add separate records, so sync needs no new rule.
- **B2 derivations (all pure, none stored):** `periods.ts` (a period = a bill + a slot, built on demand from the schedule and the facts), `timing.ts` (five mutually exclusive classes), `amounts.ts` (owed, paid, remaining; unknown is never zero), `labels.ts` (one primary label, fixed precedence, no settlement words), `cycleConflicts.ts` (contradictory evidence and look-alikes, never resolved automatically) and `readModel.ts` (the one list behind the Overview, Upcoming, Needs review and the Today card, plus the cash figures).

Markers in the Task's unknown fields: `billsObligation`, `billsCycle` (a slot), `billsPurpose` (`pay`, `notice`, `trial`), `billsDue`, `billsDeadline`, `billsDoOn`; link `task -> obligation:<id>` (`about`). One open pay Task per bill, none unless reminders are on, creation re-reads the live Tasks inside the transaction. Bills finds its Tasks by the markers on the Task row (never by the link); the `about` link is written by `createTask` and is only a pointer for other screens and the delete guard. The only removal is an untouched Bills-made Task of a paused or ended bill that stands for something no longer expected (soft delete, guarded Undo); a Task the owner touched or finished is never changed. The "no Tasks for cancel-by and trial-end" choice is the top-level obligation field `noDeadlineTasks` (an older build keeps unknown top-level fields but rewrites `reminders`).
- **B2 Calendar layer:** id `9_000_000_000_000_107` (`BILLS_ID` in `calendar/model.ts`, seeded in `calendar/data.ts`), due provider `bills` (`dueProvider.ts`). Item ids `bills:due-<bill>-<slot>:<date>` and `bills:<notice|trial|renewal>-<bill>:<date>`.
- **B2 Today card:** `bills.attention` (counts only, hidden when empty, priority 37) from `todayCards.tsx`.
- **B2 Undo:** the same local guard, extended to cover the Tasks a Bills action makes or finishes (ordinary rows in the same table) and the links those new Tasks carry (`Undo.linksAdded`).

**Bills & Subscriptions B3 additions (Finance payment links).** Still no new table, no migration, no new link type, no sync or backup change.
- **`payment-link` fact:** one more `cycle` fact. `{ obligationId, slot, fact: 'payment-link', ref: <TxnRef> }` where `ref` is the shared `TxnRef` (`txnId`, optional `splitIndex`, explanatory `snapshot`, split `fp` fingerprint) from `src/lib/txnRef.ts`: a REFERENCE, never a copy of money. Added or removed (a soft delete), never edited (`editFact` refuses); replace = remove + add in one transaction. A build that predates B3 reads the fact as unknown and carries it through every edit, so nothing is lost.
- **One money source per period:** a period's paid amount is the net of its counted Finance pieces when ANY link is in force (a typed `paid-outside` amount is then left out of every figure and listed, even if every link is stale), else the single typed amount. Writing enforces it (`paymentLinks.ts`: same piece twice refused, whole beside its part refused, linking over a typed payment needs `switchTyped`, a typed amount over links is refused); reading enforces it for what two offline devices produce (`amounts.ts`).
- **Money rules are reused, not rewritten:** `payments.ts` calls Home & Assets' `spend()` UNCHANGED with one record per period (each `pieceKey` once, a whole covers its parts, missing / split-changed / not-spending count 0 and are kept, refunds lower the net). It adds only the link roles (counted, duplicate, covered, review), Finance's own status of each counted piece (`Txn.status`: pending, cleared, reconciled; owner marks, never "settled") and the reversal test.
- **Finance is only READ, never inside a Bills transaction:** `tasks.ts` `financeLookupFor` / `inBillsTx` read the needed transactions once, in bulk, through the shared `loadTxnMap` BEFORE a write transaction opens; `readModel.ts` `loadBillsSnapshot` does the same for the screens (`financeTxns`). `periodsOf` / `derivePeriod` / `planningPeriods` take the lookup (a test fails any production call that omits it). No Bills file touches `d.txns`, and no Finance table is written (guard tests).
- **Read model and Today:** new attention categories `paymentReview`, `paymentChanged`, `partlyPaid`, `typedFinance`, `duplicatePieces` (and the autopay line now says "not yet seen in Finance"); counts and words only. New conflict kinds `typed-and-finance`, `payment-duplicate`, `payment-overlap`, `payment-shared`; the one new repair (typed vs Finance) sets the typed amount aside via the existing `use-one`.
- **Bills-only recorded payments for B5:** `billsSpend.ts` (`billsCostRecords`, `billsRecordedPayments`, `explain`): pure, over the shared `spend()`, each Finance piece once across periods and bills, flags shared pieces, explains every counted piece. It does not touch `householdSpend` (a test pins that S5's union does not mention Bills).
- **UI:** `PaymentUI.tsx` (`LinkPaymentDialog` reuses the shared `TxnPicker` with `hide`, no shared-component change; `PaymentList` reuses `RefLine`), `PaymentHistoryCard.tsx` (read only).
- **Preferences (B3.0A and B3.0B):** `services-upcoming-days` (Household Services Upcoming window: 7, 14, 30 or 90; default 30) and the Calendar's existing `calendar-hidden-layers` (now either the old list of layers switched off, or `{"only":[ids]}`; an older build treats the new form as "everything on"). Both are per-device conveniences in `localStorage`, deliberately NOT in `PREFERENCE_KEYS` (the Calendar's other view preferences are not either), never synced, never sent anywhere.

**Bills & Subscriptions B3.1 additions (discovery, match suggestions, the Finance Scheduled link).** Still no new table, migration, dependency, link type, sync rule or backup format.
- **One read-only Finance loader:** `src/lib/financeRead.ts` (`loadAllTxns`, `loadTxnsBetween`, `loadScheduled`; it re-exports only the pure `normPayee`, `detectRecurring` and `occurrencesBetween`). Bills still opens no Finance table of its own; the existing guards that forbid it are unchanged, and `b31-guards.test.ts` fails if this file ever gains a write, a posting or a forecast import, or if any other Bills file imports it unexpectedly. Finance is read in bulk BEFORE a write transaction opens, never inside one.
- **`suggestion-reject` fact (one more `cycle` fact):** `{ obligationId, slot, fact: 'suggestion-reject', ref: <TxnRef> }`. Period-scoped ("not this payment for THIS billing period"), idempotent (same operation or same piece reuses the record), added or removed (soft delete), never edited, holds a reference and snapshot, never money. A changed or reordered transaction is judged again conservatively (never a strong match). A device still on the B3 build reads it as an unknown fact: kept exactly, shown under "Needs review", never counted, never rewritten.
- **`discovery` records (new KIND of the `bills` module, no new table):** the owner's choices about recurring-expense suggestions (`not-recurring`, `dismissed`, `tracked`), one record per choice, newest wins, older ones stay as history. Fields: `key` (`p:` plus the normalised payee), `decision`, `on`, optional `obligationId`, `op`, and a small `snap` (`f`, `n`, `last`, `cents`) so a materially different pattern can be told from the same one. No transaction id, no payment list. Written only by `discoveryData.ts`; named in the backup summary as "Recurring-expense review choices". "Dismiss for now" lasts 60 days; a changed cadence, at least double the evidence (and three more payments), or a typical amount that moved by more than 25% brings a pattern back whatever was decided.

**Bills & Subscriptions B4 additions (subscription lifecycle, price history, renewals, cancellation, the Household Services link).** Still no new table, migration, dependency, sync rule or backup format. Dexie stays at version 15 with 40 tables (pinned by `b4-guards.test.ts`).
- **`lifecycle` records (a new KIND of the `bills` module, B0 10.4 "escalation path": append-only records of the same shape as the `cycle` facts).** One record is one thing the owner recorded about one obligation: `trial`, `trial-extend`, `trial-outcome`, `price-step`, `renewal`, `renewal-outcome`, `cancel-plan`, `cancel-request`, `cancel-confirm`, `cancel-withdraw`, `reactivate`, `service-link`, `ack`. Common fields: `obligationId`, `fact`, `op` (a double press saves once), `replaces` (earlier records this one corrects), `targets` (cancellation records a withdrawal or reactivation negates) and `seen` (the lifecycle ids the writing device could see, which is how two offline devices that did not see each other are told apart from one owner correcting themselves). Records are ADDED, never edited and never merged; a replaced or negated record stays visible as history. A replacement counts only when its id is later than what it replaces. Unknown fields are carried; an unknown fact type or a damaged record is listed as "needs review", counted for nothing and never rewritten. Written only by `lifecycleData.ts` (and the audit record of `crossLinks.ts`); named in the backup summary as "Subscription lifecycle records".
- **Why a new kind and not the obligation or the `cycle` kind.** The obligation is a whole-record last-writer-wins edit (one device's cancellation or price could replace the other's), and an older build would show a `cycle` record of an unknown fact as a billing-period problem. A separate kind loses nothing, needs no sync rule, and an older (B3.1) build never reads it at all (it queries only `obligation`, `cycle` and `discovery`).
- **A reader-only view, never stored.** `lifecycleRead.withLifecycle` attaches `data.lc` (the derived `LifecycleView`) to every obligation that has lifecycle records, in `loadObligations`, `getObligation` and `loadBillsSnapshot`; `toStored` drops it (a test proves a later edit never copies it into the bill). A bill with no lifecycle record has no view and behaves exactly as before. The view holds the effective records, the effective price steps, the trial and renewal in force, the cancellation in force, the conflicts and the confirmed cutoff date.
- **What the view changes elsewhere (each is a test).** `expectedAmountOn` and `currentAmount` use the effective prices (a price in dispute, or after an explicit end date, reads as UNKNOWN, never zero and never one of the candidates). `scheduleSource` stops expected periods after a CONFIRMED, undisputed effective cancellation date WITHOUT changing the stored status (the owner ends the bill). `tasks.ts` plans from the effective deadlines.
- **Tasks.** Two new `billsPurpose` values: `renewal` (only when the owner said it does not renew by itself) and `followup` (one Task the owner asked for when recording a cancellation request). A trial that ends on the cancel-by day is one deadline, not two Tasks. A recorded cancellation request means no NEW cancel-by or trial Task is made for a later date, and reminders already made are never stopped by it. A confirmed cancellation retires, with a preview and Undo, only untouched Bills-made Tasks that stand for something no longer expected; a Task the owner changed is never removed. An older build does not know the two new purposes: it treats such a Task as an ordinary Task and never touches it.
- **Attention categories (the same list feeds Overview, Needs review and Today counts):** `cancelAwaiting` (a request with no confirmation after 7 days), `lifecycleConflict` (records that disagree or cannot be read, and one Services arrangement linked from two bills), `afterCancel` (transactions that look like the subscription dated after its cancellation date), `scheduledAfterEnd` (a live Finance Scheduled payment for a cancelled or ended bill). "Leave as is" writes an `ack` record keyed to the exact evidence; changed evidence has a different key and is raised again.
- **Read-only Finance reads for these checks:** `lifecycleFinance.ts` (one date-range read of transactions after each cancellation date, and the linked Scheduled rules of cancelled or ended bills), through the existing read-only loader `lib/financeRead.ts`. It writes nothing and is the one new file listed in `b31-guards.test.ts` as allowed to use that loader. Bills still opens no Finance table of its own.
- **`bills-for` link (the optional Bills to Household Services relationship).** A plain `links` row (type `bills-for`, from `obligation:<n>` to `arrangement:<n>`), made only after the owner confirms a preview, with an audit `service-link` record and a guarded Undo in one transaction (`crossLinks.ts`, the only file that writes it). Bills never imports the Services module (a guard): arrangements are read as plain rows and the Services marker id format is pinned by a test. It never merges records, money, schedules or Tasks and changes neither `householdSpend()` nor the Bills-only recorded payments. `undo.ts` gained `linksRemoved` (Undo restores an unlinked link only if it is exactly as the action left it and no duplicate was made since).
- **Older (B3.1) build.** It keeps `lifecycle` records untouched through sync, backup and restore and never converts them; it does not know a confirmed cancellation date, so it keeps showing expected bills after it until it is updated, and it does not draw the new Calendar markers. Nothing is lost.

**Household finances additions (B5: the consolidated, read-only Overview).** Module `household` (route `#/household`, registered last in `modules/index.ts`). It owns NO record, table, link type, Calendar layer, Task, search source, Quick Add destination or Dexie version: a guard test (`b5-guards.test.ts`) fails if a household source file ever calls a database write, imports a Finance writer or the forecast, uses the network or stores anything, and pins that only `modules/index.ts` and `services/ArrangementPage.tsx` import it. It contributes exactly one thing: a counts-only Today card.
- **`unionSpend.ts`, `recordedAcrossModules(input, lookup, period)` (pure).** Does not edit, widen or replace any reader: it CALLS `householdSpend()` (S5: Services + Home & Assets, including S4's `recorded-as` rule) and `billsCostRecords()` + `billsRecordedPayments()` (B3) exactly as they are, then merges their already-resolved pieces by `pieceKey`. (This deviates from B0 12.5, which proposed extracting a `unionRecords` helper from `householdSpend.ts`: the composition gives the same totals with zero change to the spending readers, and `b3-spend.test.ts` still pins that `householdSpend.ts` and `spending.ts` never mention Bills.) A piece reached from several modules counts once; a counted whole covers a part another module links; typed amounts are simply added (never matched by value, date, payee or contact); refunds subtract; a stale reference counts nothing and is listed (and the piece still counts through any other record that validly links it). **Attribution:** the additive breakdown credits a piece to the one module whose records reach it, or to "Shared between modules"; never by list order, title or amount. Each module's own total is returned beside it, non-additive, with a reconciliation (`withinServicesHomeCents + alsoInBillsCents + coveredAcrossBillsCents = difference`). Every counted piece carries its associations (module, record, title, link, `reference` or `covered-part`), Finance's own status word, whether it changed since linking, and a plain "why it counts once"; every figure is the sum of listed pieces and authoritative typed amounts. Text it writes never contains an amount. It never calls a figure reconciled while a stale link, a possible typed/Finance duplicate, two disagreeing typed amounts or a typed payment with no amount is unresolved (`caveats`).
- **`commitments.ts`, `householdCommitments(...)` (pure).** Expected payments in 7, 30 and 90 days (today through N, both ends included) and twelve-month commitments, each split known / estimated / not known / in dispute, never adding an unknown as zero. Bills rows reuse the billing-period reader and count what REMAINS (a test pins that the sums equal `cashTiming`); the twelve months reuse `buildCommitments` (B4 prices and the confirmed cancellation cutoff) and Services' `expectedWindow` over the SAME window (Bills' own twelve months). A per-month, per-season, per-year or quoted Services estimate is not converted. It never reads Finance Scheduled or the forecast. A `bills-for` pair is folded into one commitment only when the bill and the arrangement are each other's only link, both have rows, nothing on either side is unknown or in dispute, and the totals over the window are equal to the cent; otherwise both are counted and an overlap notice states the most that could be double-counted. Home & Assets contributes none (its maintenance is Tasks with no expected cost).
- **`review.ts`, `householdReview(...)` (pure).** Needs review across modules, each item classed (informational, possible duplicate, confirmed duplicate, missing or out-of-date evidence, contractual overlap, lifecycle). It reuses the union's own items, the commitments' overlap notices and the Bills read model's lifecycle attention items; the one new rule is a confirmed cancellation date while a linked arrangement still expects visits after it. It never repairs anything.
- **`overview.ts`.** `loadHouseholdOverview(period, today, d)` reads the Bills snapshot, the Services snapshot (with its live links), the Home & Assets service records and ONE extra `bulkGet` of the transactions only Services or Home & Assets reference (Bills' own bulk read already holds the rest): no per-row read and no full transaction-table read. A failed read rejects the whole load (the page then shows an error and no totals). `buildHouseholdOverview` is the pure builder; `todayCounts` feeds the Today card.
- **Today card `household.attention`** (priority 38, half width, `hideWhenEmpty`): counts only, and only what the Bills and Services cards cannot say (possible duplicate payments across modules, a bill and a service that may be one expense, expected payments in the next 30 days with no known amount). No name and no amount.
- **Related bill on a Services arrangement (`relatedBill.ts`, `RelatedBillCard.tsx`).** Read only: reads the existing `bills-for` link through Bills' own `billsLinkedTo` and `getObligation`; never links by name; a missing, ended, paused or cancelling bill is explained, not hidden. Rendered by one added line in `services/ArrangementPage.tsx`.

## Keeping a new module backup-compatible (G1)

Backup, restore and sync work on the whole database, so a module normally needs **no backup code**:

1. Store records in the shared stores (`moduleRecords`, `links`, `contacts`, `tags`, `attachments`, `dueItems`). They are exported, restored, validated and counted automatically (a module the summary does not know is listed under "Other application data", never dropped). Optionally add its kinds to `MODULE_KINDS` in `src/lib/backupSummary.ts` so they get a friendly label.
2. Only if you add a **new Dexie table**: add it to `exportAll`/`readAll` and `importAll` in `src/lib/backup.ts`, to `OPTIONAL_LISTS` in `src/lib/backupFile.ts`, and make sure sync walks it (it walks every table). `src/lib/backupCoverage.test.ts` and the "coverage guard" tests in `src/lib/backupG1.test.ts` fail until all of these agree. That needs a migration (see `src/db.ts`) and raises `CURRENT_SCHEMA_VERSION`.
3. A new screen preference in `localStorage`: add its key to `PREFERENCE_KEYS` in `src/lib/backupFile.ts`. Never add a token, passphrase or API key.
4. Never put a secret in the `settings` table (it is exported and synced). The one exception, the price key, is filtered out of exports and never synced.
5. Records that carry files: Ledger stores names and web addresses only. Do not imply a backup contains the file.
