## A. Executive summary

Ledger already knew who is in the household and which events and Tasks name them (the "People" box). R4.2 makes that useful where people plan their week:

1. **Who it is for, everywhere.** Calendar rows, Calendar grid cells, Tasks rows and Today rows now show the household members an item names, by name and in their Family color. Several people are all shown; nobody is picked as "the" person.
2. **One person filter.** "Everyone" or one or more people, on Calendar, Tasks, Today and the new Family week. It narrows the view only; it never changes a record and never touches the Calendar's saved layer switches.
3. **Family > This week.** A day-by-day agenda of the household's week (events, dated open Tasks, birthdays and important dates), with the same filter.
4. **Print week.** A clean one-column printout from the same list.
5. **Download family calendar.** A Family-only `.ics` snapshot with an explicit dialog first.
6. **The shared Family view reader** promised in the Family plan (F0, item 7): one pure reader with an explicit audience. Only `owner` is built; every other audience (including the reserved `display`) is refused before anything is read.

No table, migration, dependency, network call, model, backup or sync change. Nothing is written by reading, filtering, printing or exporting (tests hash every table before and after).

## C. Design decisions

1. **Where the filter goes.** A slim "Family" button row, shown only when the household has two or more people. Calendar: under the toolbar, above the grid; Tasks: under the quick-add bar, above the view tabs; Today: above the status band; Family week: above the days. When someone is chosen, a status line says who is shown, what the filter does on this screen, and offers "Show everyone". The choice is kept in **this browser tab's session storage only** (`ledger-people-lens`): not the database, not a backup, not synced, gone when the tab closes, default Everyone. It is shared by the four screens so a choice carries across them, and each screen says so plainly rather than hiding it. The Calendar's layer switches (`calendar-hidden-layers`, device-local) are a different store and are never read or written by the filter (a test checks this).
2. **Colors.** The member color is an extra marker, never a repaint. Calendar items keep their calendar color, priority mark and layer name; the person appears as a name chip (lists) or small dots (crowded grid cells, where the names are still in the button's spoken label and tooltip). No second palette: the existing `--mc-*` tokens (light and dark). A member with no color is a neutral gray chip. A member who is past, unreadable or whose Contact is gone is simply not shown as a chip (never an error).
3. **Several members.** Every named household member is shown, in name order, never a "primary". Lists show up to three names then "+N" with the rest in the tooltip and the spoken text; grid cells show up to two or three dots plus "+N". In the filter, an item that names two selected people appears once.
4. **What belongs in Family week.** Calendar events naming at least one household member (the Calendar's own expander, so repeats, skipped dates and one-date changes are respected), open Tasks naming a member with a due date (or "do on" date) in the week, open dated Tasks from earlier shown as "Still open from earlier" when the week includes today, and birthdays and important dates by Family's own rules. A finished Task is never listed as outstanding. Events and Tasks that name nobody, or only a Contact who is not a household member, are not Family items (they stay in Calendar and Tasks); this is the same rule as the Family overview and a test reconciles the two. The week is the Calendar's (its first-day-of-week setting), with Previous, This week and Next. Calendars switched off on this device are counted ("N events are not shown"), not listed.
5. **What may be in the Family-only `.ics`.** An allow-list (see section E). Dated Tasks are NOT included: the Calendar's own export has no convention for Tasks, so none was invented. A birthday whose "leave off my Calendar" switch is off is not written (the owner said so for calendar files too), although the week page still lists it (as the overview does).
6. **Privacy boundary of the reader.** The owner view lives inside the signed-in household experience. The reader's contract takes an audience, serves only `owner`, and fails closed for anything else (see D). Person association is never treated as permission to display.

## D. The shared Family view reader (`src/modules/family/familyView.ts`)

- **Sources (all existing readers or rules, nothing recomputed):** `buildHouseholdActivities` (Calendar events through `occurrencesOf`), `buildHouseholdTasks` (Tasks' own `isOpen`, `isOverdue`, `sortTasks`), `datesInWindow` (new, in `upcoming.ts`, the same birthday and date rules as `upcomingRows`, for an exact window), `householdPeople` (the Overview's people).
- **API:** `buildFamilyView(audience, input, selected?)` (pure), `buildFamilyEntries` (the flat list the file also starts from), `readFamilyView(audience, query)` (reads only), `narrowFamilyView(view, selected)` (the filter, in memory, so choosing a person is instant), `entriesOf(view)`.
- **Audience contract.** `FamilyAudience = 'owner' | 'display'`; only `owner` works. `assertOwnerAudience` throws `UnsupportedAudienceError` for `display`, an unknown string, `undefined`, `null`, a different case and an object. `readFamilyView` checks the audience **before any read** (a test spies on the database: nothing is read). No display code, eligibility storage, publishing or tablet client exists.
- **Output type.** `FamilyView` { audience, from, to, people, days[{date, entries}], carriedOver, hiddenCount }; `FamilyEntry` { key, kind, title, firstDay, lastDay, allDay, startTime, endTime, recurring, status, people, link, source }; `FamilyViewPerson` { memberId, contactId, name, colorId }. No raw record, no metadata bag, no notes, location, contact detail, birth year, amount, account or tax field. A compile-time check (`expectTypeOf`) and a runtime key allow-list fail when a field is added; a test with deliberately sensitive source text (event notes and place, task notes and a linked account label, a member note and birth year, a Contact's phone and email, a Bills record, a Projects record naming the member) confirms none of it appears anywhere in the serialized view.
- **Compatibility with the Family overview.** For the same seven days, the reader returns the same event occurrences (same keys, same people), the same people (ids, names, colors), the same dated Tasks (the overview also lists undated ones; a week has no day for them) and the same dates; a stored Birthday event on the birthday is shown once, as the overview does. The Overview itself is unchanged.
- **Neutral people reader (`core/householdPeople.ts`).** Calendar, Tasks and Today must not import Family, so they read identity only (member id, Contact id, name, color id) straight from the member rows, like `core/projectLink.ts` does for projects. A test pins that it chooses exactly the people Family's `householdPeople` chooses (oldest active record per Contact; past, unreadable, unknown-role and missing-Contact rows handled alike) and that its color and role tables equal Family's.

## E. Privacy

**Owner access versus a future shared display.** R4.2 is the owner's own view. A person being named on an event does **not** make it safe for a shared tablet. The Family F0 decisions stay in force: eligibility for a shared display is a separate, explicit, revocable permission that does not exist, the default is private, and a display must never receive the whole database or sync credentials. R4.2 builds none of that (CS-0 is a separate design-only phase).

**Print week includes:** the heading and date range, who is shown, per day: time, a word for the kind (Event, Task, Birthday, Date), the title, each named person (name in text with a dot), "Repeats", Done/Overdue/Waiting/In progress. **Excludes:** all money (balances, transactions, payments, accounts), locations, notes, contact details, birth years and ages, the app's navigation and controls. Nothing is sent anywhere; Print opens the browser's own print dialog.

**Family `.ics` includes:** Calendar events that name a household member in the next 12 months (title, date and time, repeat rule, "For: names"), and family birthdays and important dates (names and labels only). **Excludes by construction (those sources are never read):** Finance, Bills, Services, Home & Assets, Projects, every other Calendar layer, Tasks, event locations, notes, reminders, tags, priority, projects, birth years and ages. A test makes every table except Calendar/Family records and Contacts throw if it is read, and a privacy test puts deliberately sensitive Finance, Bills, Services, Home & Assets and Projects records, some naming a family member, into the database and confirms none of it, and none of their money, reaches the file. Hide Amounts is not what keeps money out. Free text the owner typed into an event title is written as typed and cannot be proven private, so the dialog says so; the owner starts the download. The file is a **snapshot**, not a live calendar, and the dialog says so.

## F. User experience

- **Calendar:** filter row under the toolbar; Agenda rows show name chips under the title; Week/Month cells and timed blocks show small dots; each item's spoken label ends "for Sam and Robin". Calendar colors, layers and the Layers menu are unchanged. With people chosen, only events, Tasks and family dates that name them are listed; Finance and other money markers are hidden (the note says so) and your layer switches stay as they were.
- **Tasks:** filter row under the quick-add bar; each row shows its people; the view counts and summary are the chosen people's.
- **Today:** filter row above the status band; rows show people. **Scope is stated on the screen:** schedule, Tasks and family dates are narrowed; money items, alerts, Needs you and totals are NOT filtered.
- **Family > This week** (`#/family/week`, a "This week" button on the Family overview): Previous / This week / Next, the date range, the filter, "Still open from earlier", one card per day (a date tile, the day name, a count or "Nothing planned."), each line with a time column, a kind word, the title (a link to the Calendar event, Task or member), a status chip and the people. On a phone it is one column with no sideways scroll; empty days are one short line.
- **Print week** and **Download family calendar** are in the page header. The download opens a dialog first (what is and is not included, snapshot, nothing sent).

## H. Judgment calls (please review)

1. **The filter is shared and kept per browser tab** (session storage), so a choice on Calendar is still there on Tasks and Today. The alternative is a separate choice per screen. Each screen shows the choice and a "Show everyone" link so it cannot be forgotten silently. Say if you would rather it reset on every screen.
2. **Filtering on Calendar hides money markers.** With a person chosen, only items that can name a person are shown (events, Tasks, family dates); Finance, Bills and other layers are hidden, and the note says so. On Today they are kept (money is never filtered there). The Calendar's layer switches are untouched.
3. **"Unassigned" means Everyone only.** An event or Task that names nobody is never attributed to anyone, so it disappears when a person is chosen, and Family week never lists it (it lists only items that name a household member).
4. **A household-wide date** (an anniversary with no member) shows in Everyone and in no single person's view.
5. **Tasks are "associated with", not "assigned to"** (as in the overview): the filter is the Task's own People list and nothing else.
6. **Family week uses the Calendar's week** (your first-day-of-week setting) with navigation, not a rolling seven days from today like the overview. Past days of the current week stay visible.
7. **The family file covers 12 months, honors the person filter, leaves out Tasks, leaves out calendars switched off on this device and birthdays switched off for the Calendar.** A stored Birthday event that covers a birthday is written once (as the event).
8. **A Task with a due date but no time reads "No time set"** in the week (an event with no time reads "All day"). The Task's own "Due" versus "Do on" wording is not carried, to keep the entry type narrow.
9. **The `.ics` repeat rule is written once per series** (the Calendar export's convention), not as one entry per week.
10. **No grouping or "assign" actions, no color editing from the new screens, no per-person Calendar color mode** (the dot is an addition to the calendar color, never a replacement). An optional follow-up if the dots prove too small on a real phone is a "color by person" Calendar view; not built.
11. **A stale statement corrected:** the UI coverage roll-up said 59 pages while its rows were 60; it now says 61.
12. **Owner decisions that would improve it:** whether the filter should also appear on the Family overview (it has its own one-person version that resets each visit); whether Family week should offer a rolling "next 7 days" as an alternative; whether the file should be able to include dated Tasks once the full Calendar export (R4.3) decides how Tasks appear there.
