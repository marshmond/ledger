## A. Executive summary

**Quick Answers** lets you type a household question into Search and get a checkable answer instead of a list of pages. Ten fixed questions are supported, for example "What payments are coming up?", "Which projects are over budget?" and "How much have we spent on home maintenance this year?". Picking one opens a short answer: the number or list, the period it covers, the records behind it with links, what was assumed, what was left out, and where it came from.

How it differs from a chat assistant:

- **It is not conversational and it does not understand free text.** A typed question is matched, by simple documented word rules, to one of ten fixed questions. Anything else behaves exactly as Search always did, and Ledger says it answers a fixed set of questions.
- **Every number comes from the module that already owns it** (the same figure that module's own page shows). Nothing is estimated, guessed or written in a sentence by Ledger.
- **If it cannot answer reliably, it says so:** "Checked: nothing found", "Answered, with limits", or "Not enough information" (with what is missing and where to add it). A source that cannot be read is an error with Try again, never an empty answer or a zero.
- Nothing is written, stored or sent anywhere. There is no model, no network call, no schema or backup change, no new table.

**Ambiguous:** "what is due?", "due soon", "coming up", "upcoming", "soon" and "expected" alone are not answered; Search offers payments, services, this week and needs-attention as separate choices (and only the ones that exist).
**Unsupported:** a question that matches nothing adds no Answers row; a question-shaped search is told, once, that Ledger answers a fixed set of questions, with a "What can I ask?" link.
**Unsupported period:** "projects over budget last year" or "…in 2024" still suggests the reader, with a note that the answer is for its own fixed period.

All ten of the target questions were implemented; none was omitted. Limits are in section G.

## C. Architecture

- **Contract (`src/core/answers.ts`, pure).** `AnswerReader { id, question, title, phrases, defaultPeriod, run | Live }` and a structured `AnswerResult { status, headline (words plus typed money), period, figures, groups of rows (title, date, named amounts, chips, an internal link, source module), assumptions, limitations, sources, missing, fullView }`. The reader returns data; the screen words and draws it. `resultProblem` checks every promise (a period, at least one real source, every link inside Ledger, whole cents, `insufficient` carries a "missing" note, `limited` names its limitation) and runs in every reader's test.
- **Registry.** A small optional `contributes.answers` (`registry.ts`), validated at start-up like the other hooks (id must be `<module>.<name>`, phrases need two meaningful words, exactly one of `run`/`Live`, no duplicates). `allAnswerReaders()` lists them. `docs/module-hooks.md` documents it.
- **Module boundaries.** Each module owns its own readers (`projects.overBudget`, `bills.priceIncreases`, `assets.*`, `services.upcoming`, `household.payments`, `household.yearAhead`, `today.needs`, `today.week`) and calls its own existing reader. Search imports no module; Finance imports none. Household's answers use the same Bills/Services readers Household Finances already imports (B5's guard still passes).
- **Lazy loading.** Each module's `answerDefs.ts` is a few lines (question, phrases) read at start-up; the reader code is `import()`ed only when the question is opened, so nothing is read when the app starts or when Search opens. The two hook-based sources (Needs you, This week) are lazily loaded `Live` components that call the existing hooks.
- **Screen.** `src/shell/AnswersPage.tsx`, a shell route like Settings (`#/answers`, `#/answers/<id>`), loaded on demand; formatting and Hide amounts in `answersModel.ts`; Search rows in `searchAnswers.ts` and a small addition to `SearchDialog.tsx`.
- **Failure behaviour.** A reader that throws shows "Ledger could not read the records for this answer, so it is showing nothing" with Try again. It is never drawn as an empty answer.
- **Future-compatible, not an AI runtime.** There are no prompts, tool schemas, tokens or agents (section H).

Small changes to existing code: `OverBudgetProject` gained an additive `budgetFromLines` flag; `useWeekInputs(today, { cash: false })` can skip the Forecast read; `SHELL_PATHS` lists `/answers`; `App.tsx` has one route and one preload line.

## D. Financial correctness

- **Payments (3):** B5's own 30-day window runs to day 30 (31 days). The answer keeps B5's rows from today through day 29 and re-tallies them with B5's own `addRow`, exactly as the weekly review does for its seven days. Known and estimated amounts are separate figures and are never added. Unknown and disputed are counts; a service whose estimate is not per visit is counted under "Amount not known" the way B5's own `tally` does. A service visit folded into its linked bill is not listed or added twice; a pair that could not be proven to be one charge keeps both rows and says so. The answer says these are expected payments, not recorded transactions, and that a bill is in the Finance Forecast only when tied to an active scheduled payment; each row says "Not in the Forecast" or "Tied to a scheduled payment (may be in the Forecast)" (the answer does not read Finance, so it does not claim more).
- **Year ahead (4):** the figures are R3.1's, unchanged: Bills and services (known, estimated, not known), Finance-only, Project amounts still to pay, Important dates. No grand total and no "you will spend" sentence (a test pins both).
- **Bills (5):** an increase needs two recorded prices, one right after the other, both with amounts, the later one higher and starting inside the window. A payment above the expected price, two unrelated transactions, or a payment-timing difference are never read. "Estimated change" is labelled apart from "Recorded increase", and the percentage is shown only for a known increase.
- **Projects (6):** the figures are the project summary's (`expectedTotalCents` = paid + still to pay on accepted agreements; budget = overall budget, or the lines' total when none is set, stated on the row). A quote is not in it. A project with no budget and no lines is never over budget.
- **Home maintenance (7):** the total is the Overview's own spending reader for the calendar year (one-source costs, a payment counted once, refunds subtracted, typed amounts never mixed with linked ones), read at its "Maintenance, repairs and inspections" group. The records listed are the same cost records, each priced by the same `spend()`. A missing cost is "No cost recorded" and is never zero; a payment that needs a second look is left out of the total and said so. Checked on the demo household: the answer's $145.00 and "1 record has no cost recorded" equal the Home & Assets page's figures for 2026.
- **Overdue maintenance (8):** overdue Tasks and "finished but not saved to service history" are different lists with different words; the second is never called overdue.
- **Hide Amounts:** every money value (headline, figures, rows, notes, assumptions, the period, and an amount typed into a record name) is masked by the existing helpers. Checked in the browser on four financial answers: 0 visible dollar amounts, 24 masked marks.
- **Read only:** a test runs every reader against a real database and shows every table unchanged; another reads the answer files and finds no write, network call or storage use.

## G. Judgment calls (please review)

1. **"Home maintenance" (needs your confirmation).** I used the Home & Assets group **"Maintenance, repairs and inspections"** (service-history kinds maintenance, repair and inspection). Improvements, replacements and "other" work, an asset's purchase and recurring Household Services (cleaning, lawn care, childcare) are excluded, and the answer says so on screen. If you also want Household Services visits counted, that is a different, larger question (and would need the B5 union rules), so I did not build it.
2. **30-day and 90-day windows.** I followed the brief: today through day 29 for 30 days, today minus 89 for "recently", today through day 89 for warranties. B5's own "30 days" and the Services overview's own "30 days" run through day 30 (31 days), so a visit or payment exactly on day 30 is on those pages but not in the answer, and the answer's period always prints the real dates. Warranties use 90 days where the Home & Assets "ending soon" card uses 60, so the answer can list one the card does not.
3. **Over budget when no overall budget is set.** The Projects reader (the weekly review's) uses the lines' total as the budget. The answer lists such a project but says "No overall budget is set, so the budget is the total of its budget lines" on the row. A project with neither is never listed.
4. **Price increases are recorded changes only.** An ended bill and loan payments are skipped; a change that starts after today is not counted. A percentage is shown for a known increase only.
5. **Two ways to run a reader.** Needs you and This week exist only as React hooks, so those two readers are lazily loaded components (`Live`) rather than plain functions. It is a small second path in the contract, used by exactly two readers.
6. **This week skips the Forecast read.** `useWeekInputs` gained an optional switch; the This week page is unchanged.
7. **Ambiguity list.** "Due", "coming up", "upcoming", "soon" and "expected" alone are ambiguous. I did not add a Tasks answer, so "tasks due soon" is not one of the choices.
8. **Search order and Enter.** Answers sit after Actions so Enter on an empty box and every existing arrow-key position behave as before; example questions on an empty box sit below the Actions list, with a visible one-line hint above.
9. **Forecast wording on payments.** Because the answer does not read Finance, it says "Not in the Forecast" or "Tied to a scheduled payment (may be in the Forecast)", never "In the Forecast".
10. **Hide Amounts is read when the answer opens** (the existing behaviour on every module screen); switching it on another tab does not change an open answer until it is reopened.
11. **Per-asset amounts can add to more than the total** when one payment is linked to two records; the answer says so (the Overview's own rule).
12. **Status words.** "Checked: nothing found" (a real no), "Answered, with limits" (documented limitation), "Not enough information" (with what is missing and where to add it). A plain answer carries no chip.
13. **A new shell route, not a module.** `#/answers` is like Settings: no twelfth module, nothing on the module bar, nothing on Today.
14. **UI tracker.** Row S-24 is BLT with only `L`, `375` and `Func`; dark, 1440 and a keyboard walk are not claimed.
15. **Screenshots are kept outside the repository**, as in earlier phases.

## H. Future Ask Ledger compatibility (documentation only)

The catalog is a menu of named, parameter-free questions, each with a plain-language `question`, `phrases` and a `defaultPeriod`, and each returns a small structured, sourced result. A future, separately approved assistant (AI-D0) could be handed **only that menu** (ids and questions, no household data), return the id of the reader that fits a typed question, and then let Ledger run that reader on the device and show the answer exactly as today. The model would never receive balances, names or records; it would choose from the list, and an answer it cannot match would stay "not in the catalog". Parameters (a different period) would be added to the contract deliberately, one reader at a time, with the same checks. Nothing for that exists today and none of it is authorized: there are no prompts, tool schemas, tokens, keys or network paths.
